## ✅ 二、优点与最佳实践

### 2.1 安全设计 ⭐⭐⭐⭐⭐

**RLS 策略全面覆盖**
- ✅ 所有用户数据表都启用了 RLS（Row Level Security）
- ✅ 严格的权限分级：`own quota read`, `own orders read` 等细粒度策略
- ✅ 敏感表采用"零策略"模式（只允许 service_role）：
  - `funnel_events` - 匿名漏斗事件
  - `system_settings` - 系统配置
  - `invitation_codes` - 邀请码
  - `app_secrets` - 应用密钥
  - 所有 `assistant_*` 表 - 助理相关数据
  - 所有 `agent_*` 表 - 代理分成数据
  - 次数包相关表

**RLS 策略迭代改进历史**
- 20260922_rls_quotas.sql（第一版，失效）
- 20260922_rls_quotas_v2.sql（第二版，彻底清理所有策略后重建）
- 20260922_rls_admin_tables.sql（补齐 admin_roles, user_settings, system_settings）

### 2.2 并发控制 ⭐⭐⭐⭐⭐

**使用 PostgreSQL Advisory Locks 防止竞态条件**
```sql
-- 统一的用户级锁序
PERFORM pg_advisory_xact_lock(hashtextextended('creation:' || p_user_id::text, 0));
```

- ✅ 额度预留与扣减原子化（`kaiwu_reserve_creation`）
- ✅ 邀请码兑换防止多次兑换（`claim_invitation_code`）
- ✅ 次数包预留与结算串行化
- ✅ 联网搜索额度预占机制

### 2.3 数据完整性 ⭐⭐⭐⭐

**外键约束完整**
- ✅ 所有关联都有外键：`REFERENCES auth.users(id) ON DELETE CASCADE`
- ✅ 级联删除策略合理：
  - 用户删除 → 级联删除所有相关数据（`CASCADE`）
  - 代理删除 → 拒绝删除（`RESTRICT`，保护账务数据）
  - 作品删除 → 脚本历史解除关联（`SET NULL`，保留历史）

**CHECK 约束丰富**
```sql
CHECK (status IN ('pending','committed','released'))
CHECK (used >= 0)
CHECK (credits_remaining <= credits_total)
CHECK (char_length(content) BETWEEN 1 AND 200)
CHECK (commission_rate >= 0 AND commission_rate <= 1)
```

### 2.4 索引设计 ⭐⭐⭐⭐

**复合索引覆盖核心查询路径**
```sql
-- 作品列表（用户 + 状态 + 时间排序）
CREATE INDEX idx_works_list ON works(user_id, is_done, updated_at DESC);

-- 对标视频列表（账号 + 时间排序）
CREATE INDEX idx_benchmark_videos_account ON benchmark_videos(account_id);

-- 使用事件统计（用户 + 时间范围）
CREATE INDEX idx_usage_events_user_time ON usage_events(user_id, created_at DESC);

-- 后台监控（时间倒序）
CREATE INDEX idx_payment_orders_created_at ON payment_orders(created_at DESC);
```

**唯一索引保证业务约束**
```sql
CREATE UNIQUE INDEX idx_invitation_codes_code ON invitation_codes (code);
CREATE UNIQUE INDEX research_jobs_request_idx ON research_jobs(user_id, client_request_id);
```

### 2.5 函数式编程与安全封装 ⭐⭐⭐⭐⭐

**核心业务逻辑封装在 SECURITY DEFINER 函数中**
- `kaiwu_reserve_creation()` - 创作额度预留
- `kaiwu_settle_creation()` - 创作额度结算
- `kaiwu_web_search()` - 联网搜索额度管理
- `claim_invitation_code()` - 邀请码兑换
- `kaiwu_reserve_pack_credit()` - 次数包预留
- `save_creation_session()` - 创作会话保存

**好处**
- ✅ 权限严格控制（REVOKE ALL, GRANT EXECUTE TO service_role）
- ✅ 业务逻辑与应用层解耦
- ✅ 原子操作保证数据一致性
- ✅ 减少网络往返

## ⚠️ 三、潜在问题与风险

### 3.1 索引缺失 - 中等风险 ⚠️

#### 问题 1：大表缺少核心查询索引

**`script_history` 表**
- ❌ 缺少 `(user_id, created_at DESC)` 复合索引
- 现有索引：
  ```sql
  idx_scripts_user_id ON scripts(user_id)
  idx_scripts_created_at ON scripts(created_at DESC)
  idx_script_history_work ON script_history(work_id)
  ```
- 影响：用户查看"我的脚本历史"列表时，需要先通过 user_id 索引找到所有记录，再排序
- 建议：
  ```sql
  CREATE INDEX idx_script_history_user_time ON script_history(user_id, created_at DESC);
  ```

**`assistant_messages` 表**
- ✅ 已有 `(thread_id, created_at)` 索引，覆盖对话历史查询
- ⚠️ 缺少 `(user_id, created_at DESC)` 用于"我的所有消息"查询
- 建议视业务需求决定是否添加

**`creation_completion_evidence` 表**
- ❌ 无任何索引
- 查询场景：按 user_id 或 request_id 查询完成证据
- 建议：
  ```sql
  CREATE INDEX idx_creation_evidence_user ON creation_completion_evidence(user_id, created_at DESC);
  CREATE INDEX idx_creation_evidence_request ON creation_completion_evidence(user_id, request_id);
  ```

#### 问题 2：部分索引方向性不明确

**`payment_orders` 表**
```sql
CREATE INDEX idx_payment_orders_status ON payment_orders(status);
CREATE INDEX idx_payment_orders_created_at ON payment_orders(created_at DESC);
```
- 典型查询：管理员筛选"待审核订单"并按时间倒序
- 现状：需要两次索引扫描 + 排序
- 优化建议：
  ```sql
  CREATE INDEX idx_payment_orders_review_list ON payment_orders(status, created_at DESC);
  -- 同时保留单列索引用于其他场景
  ```

**已优化的案例**
- ✅ `funnel_events`: `(created_at DESC, kind)` - 完美匹配后台统计查询
- ✅ `works`: `(user_id, is_done, updated_at DESC)` - 覆盖用户作品列表筛选

### 3.2 N+1 查询风险 - 高风险 🔴

#### 问题 1：对标账号 → 视频列表

**数据结构**
```
benchmark_accounts (对标账号)
└── benchmark_videos (1:N 关系)
```

**风险场景**
```typescript
// 典型的 N+1 模式
const accounts = await supabase.from('benchmark_accounts').select('*')
for (const account of accounts.data) {
  const videos = await supabase
    .from('benchmark_videos')
    .select('*')
    .eq('account_id', account.id)  // N 次查询
}
```

**解决方案**
```typescript
// 使用 PostgreSQL JSON 聚合一次查询
const accounts = await supabase
  .from('benchmark_accounts')
  .select(`
    *,
    videos:benchmark_videos(*)
  `)
```

**建议**：代码审查确认前端是否存在此类查询

#### 问题 2：作品 → 脚本历史

**关联关系**
```sql
ALTER TABLE script_history 
  ADD COLUMN work_id UUID REFERENCES works(id) ON DELETE SET NULL;
```

**风险场景**
- 展示作品列表 + 每个作品的最新脚本
- 展示作品详情 + 所有关联脚本

**优化建议**
1. 如果只需最新一条：在 `works` 表添加 `latest_script_id` 字段
2. 使用 Supabase 的嵌套查询：
```typescript
const works = await supabase
  .from('works')
  .select(`
    *,
    scripts:script_history!work_id(*)
  `)
  .eq('user_id', userId)
```

#### 问题 3：订单 → 次数包批次

**关联**
```sql
count_pack_lots.order_id UNIQUE REFERENCES payment_orders(id)
```

- ✅ UNIQUE 约束保证 1:1 关系
- ✅ 索引自动创建在 UNIQUE 列上
- ⚠️ 如果查询"订单详情含次数包信息"，需确保使用 JOIN 而非循环查询

### 3.3 数据一致性风险 - 中等风险 ⚠️

#### 问题 1：会员过期后的额度重置逻辑

**代码位置**: `kaiwu_reserve_creation` 函数
```sql
ELSIF v_expired THEN
  v_free:=(p_plans->'free'->'quotas'->>(f->>'key'))::integer;
  EXECUTE format('UPDATE public.user_quotas SET %I=greatest(coalesce(%I,0),$2) WHERE user_id=$1',
    f->>'column',f->>'column') USING p_user_id,v_free;
```

**问题**
- 会员过期时，额度不是重置为 0，而是重置为**免费版额度**
- `greatest()` 函数确保不会减少已用额度
- **风险**：如果用户在付费期间已用 100 次，免费版只有 5 次，过期后显示"已用 100/5"

**建议**
- 明确产品需求：过期后是显示"超额"还是清零重新计数
- 考虑添加"上期遗留额度"字段

#### 问题 2：预留过期清理策略不统一

**次数包预留** - ✅ 自动清理
```sql
-- 每次预留前清理过期的
FOR r IN SELECT * FROM count_pack_reservations 
  WHERE status='pending' AND expires_at <= now()
```

**联网搜索预留** - ❌ 无自动清理
```sql
-- web_search_requests 表中过期记录会一直累积
```

**创作额度预留** - ❌ 无自动清理
```sql
-- creation_requests 表设置了 expires_at，但未见清理逻辑
```

**建议**
1. 统一清理策略，在所有预留函数中添加过期清理
2. 或者使用 PostgreSQL pg_cron 定期清理
3. 添加监控：预警 pending 状态超过 24 小时的记录

### 3.4 性能风险 - 低到中等 ⚠️

#### 问题 1：大字段未压缩

**`script_history.script_content` - TEXT 类型**
- 脚本内容可能很长（几千字）
- 查询列表时不需要完整内容，但 PostgreSQL 默认会读取

**优化建议**
```sql
-- 方案 1: 使用 TOAST 表（PostgreSQL 自动，确认已启用）
ALTER TABLE script_history ALTER COLUMN script_content SET STORAGE EXTENDED;

-- 方案 2: 分离大字段到独立表
CREATE TABLE script_content_store (
  script_id UUID PRIMARY KEY,
  content TEXT NOT NULL
);
-- script_history 只存 script_id
```

**`creation_completion_evidence.result` - TEXT 类型**
- 同样问题，最大 1.6MB（`octet_length(p_result)>1600000`）
- 已有 CHECK 约束限制大小 ✅

#### 问题 2：`usage_events` 表无分区

**表特征**
- 只增不改的事件日志表
- 随时间无限增长
- 查询通常限定时间范围（"最近 30 天"）

**当前状态**
```sql
CREATE INDEX idx_usage_events_user_time ON usage_events(user_id, created_at DESC);
```

**风险**
- 表超过 1000 万行后，即使有索引，查询也会变慢
- 备份和恢复时间变长

**优化建议**
```sql
-- 按月分区
CREATE TABLE usage_events_2026_11 PARTITION OF usage_events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

-- 或者使用时间序列数据库（TimescaleDB 扩展）
```

#### 问题 3：函数中动态 SQL 的性能

**`kaiwu_reserve_creation` 函数中大量使用动态列名**
```sql
EXECUTE format('UPDATE public.user_quotas SET %I=0 WHERE user_id=$1', f->>'column') USING p_user_id;
```

**问题**
- 每次调用都要重新编译 SQL
- 无法利用 prepared statement 缓存

**影响评估**
- ✅ 使用了事务级锁，并发度本来就不高
- ⚠️ 如果并发量大（>100 QPS），会成为瓶颈

**优化建议**
- 重构为静态 SQL + CASE WHEN
- 或者接受这个权衡（灵活性 > 性能）

### 3.5 备份与恢复风险 - 低风险 ⚠️

#### 问题：关键表无软删除机制

**硬删除的表**
- `works` - 作品
- `script_history` - 脚本历史
- `payment_orders` - 支付订单（状态机覆盖）

**风险**
- 用户误删除无法恢复
- 无审计追踪

**已有保护机制** ✅
- `script_history.work_id ON DELETE SET NULL` - 删除作品时保留脚本
- `payment_orders` 有状态字段（pending/reviewing/approved/rejected）

**建议**
- 核心业务表添加 `deleted_at` 字段实现软删除
- 或者依赖 Supabase 的 Point-in-Time Recovery (PITR)

## 🔍 四、特定功能深度分析

### 4.1 额度管理系统 ⭐⭐⭐⭐⭐

**设计亮点**

**三层预留-结算架构**
```
1. 检查额度 (kaiwu_reserve_creation, p_request_id=NULL)
   └─> 返回剩余额度，不锁定

2. 预留额度 (kaiwu_reserve_creation, p_request_id=UUID)
   └─> pending +1，锁定资源

3. 结算 (kaiwu_settle_creation, p_success=true/false)
   └─> committed (used+1) 或 released (pending-1)
```

**防并发设计**
```sql
-- 统一锁序：先锁用户，再锁资源
PERFORM pg_advisory_xact_lock(hashtextextended('creation:' || p_user_id::text, 0));
SELECT * FROM user_quotas WHERE user_id=p_user_id FOR UPDATE;
SELECT * FROM creation_requests WHERE user_id=p_user_id AND request_id=p_request_id FOR UPDATE;
```

**幂等性保证**
```sql
-- 重复预留返回已有结果
SELECT * INTO r FROM creation_requests WHERE user_id=p_user_id AND request_id=p_request_id;
IF FOUND THEN
  RETURN jsonb_build_object('allowed',false,'reason',
    CASE WHEN r.fingerprint=p_fingerprint THEN 'duplicate' ELSE 'conflict' END);
```

**问题与建议**
- ⚠️ `creation_requests` 表会无限增长，建议定期归档已结算记录
- ⚠️ `expires_at` 设置为 2 小时，但无自动清理机制
- ✅ 使用 `fingerprint` 字段识别重复请求，设计优秀

### 4.2 支付系统 ⭐⭐⭐⭐

**架构**
```
payment_orders (订单主表)
├── status: pending → reviewing → approved/rejected
├── proof_image_url (用户上传的付款截图)
├── count_pack_lots (1:1, 次数包订单专用)
└── payment_qrcodes (收款码配置)
```

**审核流程**
```sql
-- 管理员审核函数
CREATE FUNCTION admin_approve_count_pack_order(...)
  -- 原子操作：更新订单状态 + 创建次数包批次 + 写账本
```

**安全设计** ✅
- 订单表只允许用户读写自己的记录
- 审核操作只能通过 service_role 调用
- 状态转换有 CHECK 约束保护

**改进建议**
- ⚠️ 缺少订单号生成规则（当前使用 UUID）
- ⚠️ 缺少支付超时自动取消机制
- ⚠️ `payment_orders.amount` 使用 DECIMAL(10,2)，最大支持 9999 万元，对 B 端可能不够

### 4.3 RLS 策略演进历史 ⭐⭐⭐⭐⭐

**第一次尝试（失败）** - `20260922_rls_quotas.sql`
```sql
DROP POLICY IF EXISTS "Users can view own quotas" ON user_quotas;
CREATE POLICY "own quota read" ON user_quotas FOR SELECT USING (auth.uid() = user_id);
```
**问题**：只删除了特定名称的策略，遗漏了其他宽松策略

**第二次改进（成功）** - `20260922_rls_quotas_v2.sql`
```sql
DO $$
DECLARE pol RECORD;
BEGIN
  FOR pol IN SELECT policyname FROM pg_policies WHERE tablename='user_quotas'
  LOOP
    EXECUTE format('DROP POLICY IF EXISTS %I ON %I', pol.policyname, 'user_quotas');
  END LOOP;
END $$;
```
**改进**：枚举删除所有策略，确保干净

**经验总结** ✅
- PostgreSQL 策略是"或"关系，一条宽松策略会废掉所有严格策略
- 迁移脚本应该可重复执行
- 迁移后应该查询 `pg_policies` 验证结果

## 📈 五、性能评估与容量规划

### 5.1 表增长速度估算

| 表名 | 类型 | 预估增长 | 风险等级 |
|------|------|----------|---------|
| usage_events | 事件日志 | 100-1000 条/用户/月 | 🔴 高 |

| payment_orders | 订单 | 0.1-1 条/用户/月 | 🟢 低 |

### 5.2 索引维护成本

**当前索引总数**: 约 60+ 个

**索引覆盖率评估**
- ✅ 所有外键都有索引（自动或手动创建）
- ✅ 时间序列查询有 `created_at DESC` 索引
- ✅ 用户数据查询有 `user_id` 索引
- ⚠️ 部分表缺少复合索引（见 3.1 节）

**写入性能影响**
- 单表最多 4 个索引，影响可控
- `usage_events` 有 1 个索引 + 无更新操作 = 写入性能优秀

### 5.3 查询性能热点

**预测的慢查询**
1. 管理后台"实时监控" - 需要聚合多张表
2. 用户"历史记录"列表 - 大表全扫描风险
3. 代理"佣金结算" - 需要统计大量订单

**优化建议**
```sql
-- 1. 创建物化视图用于后台统计
CREATE MATERIALIZED VIEW admin_stats_daily AS
SELECT 
  date_trunc('day', created_at) as day,
  count(*) as event_count,
  count(DISTINCT user_id) as active_users
FROM usage_events
GROUP BY 1;

REFRESH MATERIALIZED VIEW admin_stats_daily;

-- 2. 为热点查询添加专用索引
CREATE INDEX idx_usage_events_admin_stats 
  ON usage_events(created_at, user_id, feature);
```
