# 开物运行机制与板块详解

- 版本：代码 `2eba924`（已部署线上，2026-10-31）
- 范围：档案、地基（定位与简报）、创作板块、服务端生成流水线、开物助理、偏好学习、额度
- 依据：仓库源码逐文件核对；代码里看不到的部分（Dify 工作流内部）单独标注
- 读法：先看第一、二、三节建立整体图，再看第六节按板块查。第九节列已知问题。

---

## 一、开物是什么，整体怎么运作

开物是给短视频编导和商家账号用的 AI 创作工作台。它的核心假设是：**创作质量取决于事实和定位是否先立住。** 所以产品把流程分成三层：

1. **地基层（事实与定位）**：档案（用户填的事实）→ 账号定位（六个方面的地基）→ 商业定位、内容定位（深挖）→ 创作简报（把定位翻成各板块能直接用的写作指令）。行业建议、成交理由是配套的打法和卖点。
2. **生产层（创作板块）**：起号方案、内容规划、创作方向、选题策划、脚本生成、分镜脚本、标题封面、开篇钩子、审稿优化；外加借爆款用的拆解爆款、跨行业二创、对标分析。
3. **支撑层**：服务端流水线（额度、门槛、会话、检索、事实护栏、结果后检）、开物助理（对话式派活与验收）、偏好学习（把用户的修改和收藏学成偏好卡）、知识库（编导方法论）。

**一句话的运作方式**：每个板块的页面在浏览器里，把自己需要的那部分档案和地基内容拼成一段完整提示词，发给服务端；服务端补上时间、护栏和检索词，交给 Dify 工作流（它负责知识检索和调用模型）；模型的输出经过若干后检，再存进历史。

```
档案 ──► 账号定位(01) ──┬─► 商业定位(02) ──┐
  │                    └─► 内容定位(03) ──┤
  │                                       ▼
  └────────────────────────────► 创作简报(04) ──► 各板块按清单切片取用
                                              │
行业建议(05) ───────────────────────────────► │
成交理由(17) ───────────────────────────────► │
                                              ▼
内容定位系列 ──► 内容规划(07) ──► 创作方向(08) ──► 选题策划(09) ──► 脚本(10) ──► 分镜(11) / 标题(12) / 审稿(14)
                                                                 ▲
拆解爆款(16) / 跨行业二创(15) / 对标分析(18) ─── 借外部爆款的结构，输出可复刻的方向
```

## 二、数据从哪里来（事实来源）

| 来源 | 存什么 | 谁写入 | 谁读取 |
|---|---|---|---|
| 档案 `user_profiles` | 账号名、平台、赛道、阶段、粉丝量级；人群；产品品类；人设事实卡（出镜人是谁、年限、籍贯、店的关系）；访谈要点；卖点；拍摄条件（场地、设备、团队）；禁忌（绝对不能说）；排除清单 | 手填；前采建档确认后写入 | 几乎所有板块（经 `buildProfileSummary` 和 `buildContextBlock`） |
| 账号定位 `account_positioning` | 类型为「账号定位」「商业定位」「内容定位」「创作简报」的全文，`is_active` 标记当前生效的那份 | 对应的定位板块生成后保存 | 定位链上的下游板块；事实核对（`factMaterial`） |
| 生成历史 `script_history` | 每次生成的输入和结果，按档案 `profile_id` 归属 | 服务端 `persistCreativeHistory`，或旧版客户端保存 | 历史页；**历史不再回灌进新生成**（2026-10-31 起） |
| 偏好卡 `preferences` | 用户改稿、收藏、选题的行为学出来的表达习惯（口吻、开头、结构、内容取向），至少在 3 个不同内容里出现才生效 | 偏好学习（服务端 `recordGenerationSignal` 等） | 写稿类板块的上下文（`preferencePromptBlock`） |
| 地基进度 | 建档、账号定位、创作简报三步是否完成 | 各步保存时 | 门槛判断（`foundationGate`） |
| 知识库 | Dify 里的编导方法论文档（源文件在 `编导知识大全/_导入Dify/`） | 导入 Dify | Dify 工作流按 `search_query` 检索 |
| 用户原话 | 页面输入的想法、个人要求、已有的稿子、锁定的开头 | 用户 | 对应板块的提示词和护栏 |
| 选题库 | 这个档案已出过的选题标题 | 选题生成后 | 选题策划的「不许重复」清单（`loadPriorTopicTitles`） |

## 三、地基门槛：没有地基，不生成

`lib/foundation-gate.ts` 规定了每个任务生成前至少要有什么：

| 任务 | 需要的地基 |
|---|---|
| 自由对话、知识库查询、AI 推荐、前采建档 | 不需要（它们本身就是在建地基，或只回一段配置） |
| 账号定位 | 有档案 |
| 商业定位、内容定位、创作简报 | 账号定位已做好 |
| 其余所有创作任务（选题、脚本、分镜、标题、方向、起号、拆解、二创……） | 账号定位和创作简报都做好（默认就是三步全做完） |

门槛在扣额度之前判断，拦下来不扣额度，并告诉用户先去做哪一步。推荐的使用顺序（帮助页）：前采建档（可选）→ 个人档案 → 账号定位 → 创作简报 → 内容规划 → 创作方向 → 选题策划 → 起号（开篇钩子）→ 脚本生成 → 审稿优化 → 分镜脚本 → 标题封面 → 创作进度。

## 四、上下文分发：每个板块拿到什么

上下文清单在 `lib/context-manifest.ts`（`BOARD_MANIFESTS`）。这张表决定每个板块能看到档案的哪几块、要不要简报、要不要成交理由、要不要深挖的定位。它的设计原则是「加板块就加一行，改分发就改这一行」，并有测试逐板块核对。

档案切成 8 块：`account`（平台、赛道、阶段、粉丝量级）、`audience`（人群、痛点、需求）、`tone`（语气、风格）、`selling`（卖点、内容价值、已验证的钩子）、`shooting`（设备、团队、场地、预算）、`monetize`（变现方式、价格区间、成交路径）、`viral`（爆款基因、差异化、已有方向）、`restrictions`（绝对不能说）。

| 板块 | 档案切片 | 简报字段 | 成交理由 | 深挖定位 | 职责（清单里的原话） |
|---|---|---|---|---|---|
| 选题策划 | account、audience、viral、restrictions | 无（方案 D：避免简报把没依据的时间、流程带进选题） | 要 | 内容定位的系列 | 找往哪个方向拍 |
| 脚本生成 | account、audience、tone、selling、restrictions | 无 | 要 | 商业定位的成交路径（结尾要对上） | 决定怎么说：口吻、说服点、记忆点 |
| 分镜脚本 | account、shooting、restrictions | 无 | 不要 | 无 | 决定怎么拍：只关心拍摄条件和画面 |
| 审稿优化 | account、audience、tone、restrictions | oneline、persona、audience、forbidden | 不要 | 无 | 当判据用：语气、人群、禁忌 |
| 标题封面 | account、audience、selling、restrictions | oneline、audience、trust、forbidden | 要 | 无 | 给谁看、凭什么点 |
| 成交理由 | account、audience、selling、monetize、restrictions | oneline、audience、trust、forbidden | 不要（它本身产出成交理由） | 无 | 找凭什么让人买 |
| 起号方案 | account、audience、tone、shooting、monetize、viral、restrictions | oneline、persona、audience、direction、shooting、forbidden | 不要 | 内容定位（页面另传系列清单） | 挑他拍得出来的打法 |
| 高阶自由对话 | account、audience、tone、selling、shooting、restrictions | oneline、persona、audience、direction、trust、shooting、forbidden | 不要 | 无 | 随口问什么都可能，给一份账号全貌 |
| 拆解爆款 | restrictions（档案摘要另传） | oneline、audience、direction、forbidden | 不要 | 无 | 拆完给 5 个变现方向，带可复刻结构 |
| 跨行业二创 | restrictions（档案摘要另传） | oneline、persona、audience、trust、memory、forbidden | 要 | 无 | 把别的行业的爆款换成这个账号的血肉 |
| 创作方向 | monetize、viral、restrictions | 无（方案 D） | 要 | 内容定位的系列 | 带着目的找方向 |
| 知识库 | account、restrictions | oneline、audience、forbidden | 不要 | 无 | 答方法论问题，举例用他自己的行业 |

这张表是**设计意图**。实际运行中有两处页面直接传参，与表有差异，见第九节。

## 五、一次生成请求，服务端按什么顺序处理

入口是 `app/api/dify/stream/route.ts` 的 `POST`。按代码顺序：

1. **读请求体**。请求可能是压缩或分块发来的（`lib/read-body`）。
2. **登录和额度**。`requireUserWithQuota(feature)` 按功能检查额度（免费版每个板块的次数以帮助页为准）。
3. **档案归属**。有档案的用户，创作请求必须带档案编号；之外的任务（知识库、自由对话、前采建档、AI 推荐）不需要（`PROFILE_OPTIONAL_TASKS`）。档案编号必须属于当前用户。
4. **地基门槛**。`foundationGate`，见第三节。不通过就返回提示，不扣额度。
5. **历史归属检查**。创作类任务（`DURABLE_CREATIVE_TASKS`）确认历史要写入的档案属于当前用户。
6. **选题不重复**（仅选题策划）。`loadPriorTopicTitles` 取这个档案出过的标题，附上「不许重复」清单；若用户选中了方向要落实，则改为「落实已选方向」。
7. **拼创作设置**。`creationSettingsBlock`：目的、人群、结构、拍法、开头、禁忌、用户原话等。
8. **时间锚**。若提示词里没有「今天是 X 年」，补上当前日期和季节（`timeAnchor`）。模型自己不知道今天几号。
9. **事实护栏**（除 AI 推荐、前采建档外）。从档案里取关键事实原话（`profileFactsBlock`），在提示词最末尾加「别把设想写成真事」（`factGuardTail`），并把用户明确说不要的内容列出来（`userDonts`）。同时把档案全文、账号定位、创作简报放进「事实核对的已知素材」，给后检用。
10. **历史回灌**。`loadCreativeMemory` 现在返回空，不再把历史方向名字或正文拼进去（2026-10-31 起）。
11. **组装 Dify 请求**。`inputs` 里有 `query`（完整提示词）、`search_query`（短检索词）、`conversation_history`、`dealReasons`；`user` 是真实用户 id（Dify 按它隔离会话和用量）；可带上传的图片。
12. **检索词**。`buildSearchQuery`：创作类任务只用任务的主题词（比如创作方向：「内容方向 内容配比 流量型 人设型 变现型 选题来源 起号打法 成交路径」），加上档案的赛道和地域（联网搜索要的事实）。档案名、行业、选题、用户想法不进检索词（2026-10-31 起）。
13. **会话**。隔离名单里的任务（`ISOLATED_TASKS`，包括全部创作板块）不读共用会话，每次都是独立对话，不保存新会话 id。自由对话、知识库等读写「用户 + 档案 + 功能」作用域的共用会话。
14. **预留额度**。`reserveCreation`，生成成功后再记完成。
15. **调用 Dify**。`POST {DIFY_BASE_URL}/chat-messages`，流式返回。**Dify 工作流内部**（5 个知识检索节点、模型选择、工作流节点）不在仓库里，本报告未核对。
16. **流式接收**。网络断了会用 `waitForDifyMessage` 取回已写完的结果，不重复扣费。
17. **后检**（按任务类型依次进行，见下表）。
18. **存档与计费**。`persistCreativeHistory` 写入历史；`recordCreationCompletion` 完成额度结算；`incrementUsageServer` 计次；`recordGenerationSignal` 记学习信号。

**第 17 步的后检**（按顺序，各有触发条件）：

| 检查 | 作用 | 触发条件 |
|---|---|---|
| 条数与长度复核 | 检查输出的条数、长度是否符合要求，不符则让模型修一次 | 有明确条数要求的任务（`boundedResultIssues`） |
| 去内部标签 | 清掉提示词里的内部标记（`sanitizeOutput` / `stripInternalLeaks`） | 所有生成 |
| 脚本修复 | 脚本长度、口播段不合格时，让模型按原因修一次（`scriptRepairReason`） | 脚本生成 |
| 事实核对与修正 | `unsupportedFacts` 和 `seasonMisstatements` 找出没有依据的事实和季节错误，让模型修（每用户有限次） | 事实自动修复任务（`FACT_AUTO_FIX_TASKS`） |
| 细节核查 | 另一次模型调用检查细节，必要时修正 | `DETAIL_CHECK_TASKS` |
| 说话人检查 | 检查出镜人和受访者的称呼、人称是否串了 | `SPEAKER_CHECK_TASKS` 且 `needsSpeakerCheck` 为真 |
| 证据护栏 | 没有依据的内容被挂起（`holdUnsupported`） | 有事实问题时 |
| 年份修复、现实性修复 | 修正年份；修正明显不真实的句子 | 视内容而定 |
| 审稿原稿校对 | 审稿任务单独调模型，对照原稿核对事实（180 秒超时） | 审稿优化 |
| 标题数量复核 | 标题条数对齐 | 标题封面 |
| 结构块保持 | 拆解的 JSON 结构不被整理步骤改坏（`keepStructureBlock`） | 拆解爆款 |

后检是**多次额外模型调用**，一次生成可能触发不止一次。

## 六、各板块详解

每个板块包括：职责、输入、依赖、提示词组装、生成步骤、输出去向、注意事项。

### 6.0 前采建档（前采提取，第 19 节）

- **职责**：把前采（访谈）记录整理成档案字段，是档案的原料入口。
- **输入**：粘贴的文字，或上传的 .docx、.txt。
- **提示词**：`buildExtractionPrompt(source)`。
- **步骤**：模型提取出 JSON 字段，每项标注原文依据；用户在确认页逐项核对；可以用「跟 AI 说哪里不对」让它改对应的几项（不扣次数）；确认后写入新档案或已有档案（`/api/interview/save`）。
- **输出去向**：档案字段。之后所有板块都读它。
- **注意**：手机号、身份证号不进档案。前采原文和提取历史可在历史里删除。

### 6.1 档案（不是生成板块，但它是全部板块的依据）

- **字段**：见第二节。`buildProfileSummary` 把它整理成一段摘要，供所有板块共用；`buildContextBlock` 按第四节的清单切片。
- **排除清单**：建档时用户刻意没选的内容，相关句子先从档案里拿掉，再进提示词（`scrubProfile`）。
- **人设事实卡**：出镜人是谁、年限、籍贯、店的关系，是最硬的事实，每个板块都带。

### 6.2 账号定位（第 01 节）

- **职责**：给账号立地基：这个号是什么主体、说给谁听、凭什么信你、长期做什么。
- **输入**：档案摘要、平台、作用配比（若已定）。
- **提示词**：`buildPositioningPrompt`，`focus` 为 `full`（默认）。组成：角色（资深编导）、立场（接手这个号）、行业视角、六维地基（IP 定位表）、人设七个入口、内容方向（多元四类或单一主题）、内容配比（五步）、呈现形式、记忆点、差异化、经济模式、自洽检验、输出格式。
- **步骤**：先判断主体（店、人、品牌）→ 立六维地基 → 选人设入口 → 定内容方向和配比 → 检验自洽 → 输出。
- **输出**：账号定位全文，存为 `账号定位`，设为当前生效的那一份。
- **注意**：这是提示词体量最大的板块之一（A 行业约 2.5 万字符）。

### 6.3 商业定位（第 02 节）

- **职责**：拆通变现路径：怎么赚钱、成交步骤、凭什么让人买。
- **输入**：档案摘要、账号定位（`baseline`）。
- **提示词**：`buildPositioningPrompt`，`focus` 为 `business`。
- **输出**：商业定位，存为 `商业定位`。脚本的结尾动作要对上它的一步（清单的 `deep: business`）。

### 6.4 内容定位（第 03 节）

- **职责**：定内容方向（多元四类，还是单一主题）、系列、配比。配比是全站唯一来源，其他板块的数字都从这里来。
- **输入**：档案摘要、账号定位、作用配比块（`mixBlock`）。
- **提示词**：`buildPositioningPrompt`，`focus` 为 `content`。
- **步骤**：先定方向 → 再定作用配比（流量、人设、变现的比例，有配比块就照抄）→ 再定形式和题材（只写主次，不写百分数）→ 系列设计 → 选题来源 → 差异化 → 自洽检验。
- **输出**：内容定位，存为 `内容定位`。它的系列清单是选题和创作方向的深挖参考（清单的 `deep: content`）。

### 6.5 创作简报（第 04 节）

- **职责**：把定位翻成各板块能直接用的写作指令，是地基到生产的主通道。
- **输入**：账号定位全文、档案摘要、用户备注、商业定位、内容定位、配比块。
- **提示词**：`buildBriefPrompt`。
- **输出**：一份 markdown 简报，存为 `创作简报`。它按字段切片（`BRIEF_FIELDS`：oneline 一句话定位、persona 人设、audience 人群、direction 方向、trust 凭什么信你、shooting 拍摄条件、memory 记忆点、forbidden 禁忌），由清单决定每个板块拿哪几个字段。
- **注意**：选题和脚本**不拿**简报（方案 D：简报是模型转译出来的，会把没依据的时间、流程带进去）。这是有意的。

### 6.6 行业建议（第 05 节）

- **职责**：按账号目的和阶段，给一套行业打法（药方）。
- **输入**：档案摘要、账号定位、商业定位、内容定位（作为框架），加上账号目的（流量、人设、变现、阶段性）、阶段（起步、积累、放大、变现）、现状、目标、作品数据（若有）、禁忌。
- **提示词**：`buildIndustryAdvicePrompt`。
- **步骤**：先判断行业视角 → 在定位框架内选和排打法 → 给出阶段重心（主力还是辅助，只写主次）。
- **输出**：行业建议，存为 `行业建议`。起号方案等板块会按它执行。

### 6.7 成交理由（第 17 节）

- **职责**：找凭什么让人买：卖点、顾虑、成交理由。
- **输入**：档案摘要、门店名、门店类型、门店特色、目标客户。
- **提示词**：`buildDealReasonPrompt`。
- **输出**：成交理由清单，保存后，脚本、标题、二创等板块会自动带上（`dealReasons` 标志）。
- **注意**：成交理由本身不读旧的成交理由。

### 6.8 起号方案（第 06 节）与开篇钩子（第 13 节）

- **职责（起号）**：新号前几条怎么拍。挑「他拍得出来的」打法，给起号期配比、怎么测、30 天节奏。
- **输入**：起号的上下文（档案的 account、audience、tone、shooting、monetize、viral、restrictions，加简报的 oneline、persona、audience、direction、shooting、forbidden）、内容定位的系列清单（页面参数 `contentPlan`）、配比块。
- **提示词**：`buildGrowthPlanPrompt`。组成：起号期配比、36 计的选择规则（禁忌里的计要排除，`tacticsBlockedBy`）、四大脚本、写作要求（配比只出现在作用配比上，篇幅 4000 字硬上限）。
- **步骤**：对照拍摄条件和禁忌筛 36 计 → 挑一计作主攻 → 给备选 → 定起号期配比 → 怎么测 → 30 天节奏 → 跑不通先查哪里。
- **输出**：起号方案，存为 `起号方案`。
- **职责（开篇钩子）**：给 3 个开头，横向比较，选定后脚本必须用这一句（`openingLine`）。
- **提示词**：`buildOpeningPrompt`，参数是上下文（起号上下文）、选题、条数（3）、意图（目的、方向、用户原话）。
- **注意**：起号和开篇都在「起号」页面，页面用的是同一份起号上下文。

### 6.9 内容规划（第 07 节）

- **职责**：按配比排出一批内容的目的和主题（默认 12 条），是方向的上游。
- **输入**：档案摘要、作用配比（`resolved`）、上期内容（若有）、近期事件、备注、上下文（定位的系列清单，由 `buildContextBlock(context, "direction")` 带入）。
- **提示词**：`buildContentPlanPrompt`。
- **输出**：内容规划，存为历史。它与内容定位的系列一起，是创作方向的参考（`contextBlock`）。

### 6.10 创作方向（第 08 节）

- **职责**：带着目的找方向：这一批内容分成几个方向，每个方向有目的、形式、拍法。
- **输入**：目的（流量、人设、变现、信任等）、形式（过程、教学、谈话等）、配比块（条数）、上下文（内容定位加内容规划）、档案摘要、用户想法（「已有的想法」）、要拓展的已有方向（若从别的板块带过来）、36 计和四大脚本的选择（两派只选一派）。
- **提示词**：`buildDirectionPrompt`。组成：目的与形式、上下文、36 计索引（禁忌计已排除）、四大脚本、配比块、创作规则（`creativeCraftRules`，含新加的「参考里的具体时段、地点、食材，只有本次输入写到的才能用」）、创作设置。
- **步骤**：先看目的和形式 → 对照内容定位和规划 → 选方向 → 每个方向写出目的、拍法和一句话的理由。
- **输出**：方向清单（`### 方向N：名字`），供选题策划使用。
- **注意**：创作方向在隔离名单里，不读共用会话，也不读历史（历史回灌已关闭）。

### 6.11 选题策划（第 09 节）

- **职责**：把方向细化成可以直接拍的选题：每条有视频目的、一个打法（36 计或四大脚本，二选一）、爆款元素、标题。
- **输入**：创作方向的输出（前 4000 字）、选题数量（6）、路线（两种都出）、配比块、「已出过的选题」清单（不许重复）、是否带钩子、用户的选题要求。
- **提示词**：`buildTopicBoardQuery`。
- **步骤**：从方向里挑出可拍的事件 → 给每条选题定目的 → 选一个打法（36 计看事件走向，四大脚本看讲法）→ 配爆款元素 → 写标题 → 与已出过的选题查重。
- **输出**：选题清单。用户选中一条，带去脚本生成。
- **注意**：选题**不带简报**。它的重复控制靠数据库里的选题库，不靠会话记忆。

### 6.12 脚本生成（第 10 节）

- **职责**：把选中的选题落成可以拍的完整脚本：策略卡、口播文案、分镜、执行建议。
- **输入**：选中的选题标题、选题清单（原文）、平台、时长、目的（`effectiveRole`）、行业、档案、账号定位（页面直接传全文，见第九节）、脚本结构、钩子类型、爆款元素、导演思路、拍法（36 计）、用户选定的开头（`openingLine`）、成交理由、创作设置。
- **提示词**：`buildScriptBoardQuery` 决定走哪条路径：
  - **非广告（默认）**：`buildAdaptiveScriptPrompt`（`lib/script-design`）。组成：输出规则块（`outputRulesBlock`，含【待确认】占位规则）、创作设置、内容树（结构已定，不另选）、拍法指引（两派只选一派）、钩子指引、结构指引、创作规则（`creativeCraftRules`）、内容质量要求（含新加的占位与个人习惯句规则）、输出格式（策略卡、口播、分镜、执行建议）。
  - **广告引流**：广告模板（`fourStepWorkflow`），第 3 步有【待确认】规则，全篇不超过 2 处。
- **步骤**：策略卡（核心问题、目的、人群、形式、材料递进、事实边界、流量型的出发点）→ 口播文案（只写能直接念的话，一句一行）→ 分镜（按台词字数定时长，每个镜头标时间和拍摄要点）→ 执行建议（拍前要确认的事、资料缺口）。
- **输出**：脚本全文，存为 `脚本生成`。
- **后检**：脚本修复（长度、口播段）、事实核对、说话人检查、现实性修复。

### 6.13 分镜脚本（第 11 节）

- **职责**：把脚本拆成镜头，决定怎么拍。
- **输入**：脚本全文、时长（默认「按脚本长度」）、内容类型（美食、探店、教程、产品、故事、采访）、视觉风格、档案的拍摄条件（account、shooting、restrictions；不带简报）。
- **提示词**：`buildStoryboardPrompt`。组成：镜头时长规划（`planShots`，按台词字数和语速 5 字/秒）、景别语言、运镜（按真实拍摄条件，`cameraMoveGuide`）、画面与台词的关系、剪辑衔接、平台框架、拍摄要点（只写拍的动作、景别、收音或安全，不写台词规则）。
- **步骤**：按台词字数排镜头时长 → 每镜定景别和运镜 → 写画面、台词、拍摄要点。
- **输出**：分镜表。`auditStoryboard` 检查总时长与台词是否对得上，念不完的镜头会被标出。
- **注意**：分镜表里的台词禁忌同样适用，所以分镜也带 restrictions。

### 6.14 标题封面（第 12 节）

- **职责**：给脚本或选题配标题和封面文案。
- **输入**：选题标题、标题类型（如痛点式）、标题公式（如数字加动作）、关键词策略、平台、目标人群、档案（account、audience、selling、restrictions）、源内容（脚本）。
- **提示词**：`buildTitlePrompt`。
- **步骤**：按公式和类型写标题 → 带关键词 → 配封面文案 → 与人群痛点对齐。
- **输出**：标题与封面文案，存为 `标题封面`。后检包括条数复核，以及「万能模板标题」的精准小改（`title-polish`）。

### 6.15 审稿优化（第 14 节）

- **职责**：当判据用：语气对不对、说的是不是这群人关心的、有没有踩禁忌、事实有没有依据。
- **输入**：待审的稿（脚本）、审稿维度（页面选择，如逻辑、过渡、语气）、严重度标签、优化目标、可选的对标稿、档案（account、audience、tone、restrictions）、简报（oneline、persona、audience、forbidden）。
- **提示词**：`buildReviewBoardQuery`。
- **步骤**：逐维度检查 → 标出问题并给严重度 → 给修改建议（只给建议，不替用户改写整稿）。
- **后检**：`reviewVerificationPrompt` 另起一次模型调用，对照原稿核对事实；输出的内部标签会被清掉（`stripInternalLeaks`）。
- **输出**：审稿报告，存为历史。

### 6.16 拆解爆款（第 16 节）

- **职责**：拆别人的爆款文案（或截图、视频材料）：找结构、钩子、情绪；然后给 5 个变现方向，每个方向都是可复刻的二创结构，选中后带去其他板块裂变。
- **输入**：粘贴的原文（或截图拼图）、上下文（restrictions 加简报的 oneline、audience、direction、forbidden）、创作设置。
- **提示词**：`buildTextBreakdownPrompt`。组成：工作任务、材料类型（纯文字时不能编镜头、秒数、播放量）、待拆解内容、拆解知识分类（`taxonomy`）、6 点输出要求（1–4 点拆解，第 5 点优化后的完整文案，第 6 点 5 个方向的 JSON）、篇幅（1–4 点合计 1500 字；第 6 点每段 do、lines 不超过 30 字；5 个方向目的各不相同；goal 只写类型词；第 4 点之后不加小节）、先判断材料是谁的（同行的稿子只借鉴结构，不把对方的经营事实写成这个账号的事实）。
- **步骤**：判断主题、方向、人群、视频目的（只判断一个主目的）→ 找出发点（人货场、三有、爆款元素）→ 逐项拆开头、结构、信息递进、情绪、结尾 → 写能保留和需要优化的部分 → 给一版承接原意的优化文案 → 按模板给 5 个方向。
- **输出**：拆解报告；方向 JSON 由页面渲染成卡片。`keepStructureBlock` 保证 JSON 结构不被后面的整理步骤改坏。
- **注意**：方向 JSON 的结构由 `lib/breakdown-templates.ts` 的 TEMPLATE_SPEC 决定，页面按它渲染。字数大，是结构决定的。

### 6.17 跨行业二创（第 15 节）

- **职责**：把别的行业的爆款换成这个账号的血肉：保留结构，换题材、人物、场景、说法。
- **输入**：原爆款（粘贴或选中的拆解方向）、层级（`DEFAULT_LAYERS`）、输出（`DEFAULT_OUTPUTS`）、数量（3）、角色（同一人或不同人）、时长、门店信息（店名、特色、赛道）、上下文（restrictions 加简报的 oneline、persona、audience、trust、memory、forbidden，以及成交理由）。
- **提示词**：`buildRemixPrompt`。
- **步骤**：拆原爆款的结构 → 换成这个账号的人设、人群、记忆点 → 成交理由放在结尾当说服点 → 输出 3 个版本。
- **输出**：3 个二创版本。

### 6.18 对标分析（第 18 节）

- **职责**：拆对标账号：它的结构、打法、选题分布，并说明每条结论依据哪份材料。
- **输入**：对标账号名、平台、材料清单（截图、文字、视频说明）、文字资料、账号背景（档案摘要，只用于「对我们的参考」）。
- **提示词**：`buildBenchmarkQuery`。组成：固定框架（账号定位、内容打法、选题类型分布、开头钩子、视频结构、时长规律）、依据规则（每条结论标明依据；样本少于 10 条注明「样本不足」；样本少于 3 条不写占比、百分数、「占 100%」）、结构归类只能从注册表里选。
- **输出**：对标分析报告。它的结论只说「相关」，不写「因为……所以……」。

### 6.19 自由对话（高阶）

- **职责**：什么都能问：出方案、读图片和文档、联网查资料、深度研究入口。
- **输入**：用户的问题、会话历史（共用会话，作用域为用户加档案加功能）、上下文（freeChat 的切片）、联网模式（默认关闭，按需开启并扣额度）。
- **提示词**：页面拼的完整问题加上下文。
- **步骤**：读上下文 → 回答问题；需要时联网（`prepareWebSearch`）。
- **输出**：回答。可以通过「继续创作」把成稿带给其他板块（`carry`）。
- **注意**：自由对话**读共用会话**，所以它的回答会被后续问题带着走；这是有意的（对话需要延续），但也是本次排查里要留意的通道之一。

### 6.20 知识库

- **职责**：答方法论问题（编导知识库），举例用这个账号自己的行业。
- **输入**：用户的问题（同时作为检索词）、上下文（account、restrictions 加简报的 oneline、audience、forbidden）。
- **检索**：Dify 知识库节点按检索词召回文档。
- **注意**：知识库里的示例句（如「一天的开店日常：凌晨四点我来到市场的样子」）可能被召回。这份知识库的内容由用户维护，代码层面只能收窄检索词，不能过滤内容。

### 6.21 深度研究

- **职责**：长篇研究（多步骤、带来源），独立接口 `app/api/research`，与地基门槛共用同一套判断（`foundationGate`）。
- **本报告未逐行核对**其内部流程。

### 6.22 开物助理（对话式派活与验收）

- **位置**：右下角的助理窗口（`components/assistant/AssistantWidget`），以及助理页面（`/dashboard/agent`）。
- **职责**：用户用一句话让助理做事：查档案、列任务、派活给某个板块、验收结果、把成稿带给其他板块。
- **运作**：
  1. **对话循环**（`lib/assistant/agent.ts`）：模型决定调用哪个工具，把结果交回去，直到给出回复。每一步都告诉界面正在做什么，步数有上限，用户可随时停止。
  2. **工具**（`lib/assistant/tools.ts`）：查档案、列可派的任务、派活。派活前先用地基门槛拦截（跑不了的任务不让老板确认）。
  3. **板块调度**（`lib/assistant/board-dispatch.ts`）：16 类板块（`BoardKind`）各自对应一个功能名（额度）和显示名。内容规划和创作方向共用一项额度。
  4. **验收**（`lib/assistant/manager.ts`）：管理员式的两道关。第一道是确定性规则：每类产出的最低长度（如脚本 300 字、选题 200 字）、脚本质量、事实依据。第二道是模型对照派活要求再判一遍。不过关时，只做「原文一句 → 改后一句」的精确替换，最多两次，不整份重跑（避免重复扣额度）。
  5. **带内容**（`lib/assistant/carry.ts`）：把成稿带到另一个板块，保留设置和来源。
- **注意**：助理派活的板块，生成规则与直接在板块页面使用的完全一样（同一条服务端流水线）。

## 七、规则体系：提示词里有哪些共用规则块

这是理解「规则为什么多」的关键。所有板块的提示词由几类共用块拼成，每一类都在多个板块里出现：

| 规则块 | 文件 | 作用 | 被哪些板块用 |
|---|---|---|---|
| 时间锚 | `lib/time-anchor` | 告诉模型今天的日期和季节 | 服务端所有生成（除已有日期的） |
| 创作设置块 | `lib/creation-settings` | 目的、人群、结构、拍法、开头、禁忌、用户原话、锁定片段 | 脚本、方向、选题、二创等 |
| 事实护栏 | `lib/fact-guard` | 档案关键事实原话；「别把设想写成真事」；用户说不要的内容 | 服务端所有创作（除 AI 推荐、前采建档） |
| 本轮内容落实规则 | `lib/creative-craft` 的 `creativeCraftRules` | 目的与主体；已有稿子只作草稿；说话人规则；采访规则；比较口径；参考里的具体细节只有本次输入写到才能用 | 脚本、方向、开篇、审稿、分镜等 |
| 输出规则 | `lib/output-rules` | 【待确认】占位只用于真想写具体数字又没有资料时；输出的优先级 | 脚本、选题、审稿 |
| 事实清单 | `lib/fact-inventory` | 清单之外的数字一律不写 | 脚本、选题、审稿 |
| 配比块 | `lib/content-mix` 的 `mixPromptBlock` | 作用配比（流量、人设、变现）的唯一来源；形式和题材只写主次 | 定位、简报、起号、方向、规划、选题 |
| 拍法（36 计、四大脚本） | `lib/creative-routes`、`lib/growth-tactics`、`lib/script-route` | 两派只选一派；禁忌计排除 | 起号、方向、选题、脚本 |
| 内容树 | `lib/creation-tree` | 选题写明了结构，脚本就按它；不另选 | 脚本 |
| 真实性规则 | `lib/sharp-rules` 的 `REALITY_RULE`、`PRODUCT_HERO_RULE` | 不编经历、不编产品效果 | 脚本、二创 |
| 偏好卡 | `lib/preferences` 的 `preferencePromptBlock` | 用户学出来的表达习惯；带具体场地、设备、时段的不拼进去 | 写稿类板块（上下文里） |
| 禁忌 | `restrictions`（档案）、`taboos`（平台红线、行业禁忌） | 硬约束，不能说、不能拍 | 所有板块 |

**规则多的原因**：每个板块的提示词都要同时满足：事实不编、结构对、口吻对、禁忌不踩、长度对、格式对。这些约束由不同的块分别写入，同一条规则（比如「占位」「配比」）在多个块里重复出现，因为各板块是独立拼装的。这是第九节「规则太多」问题的根源之一。

## 九、已知问题与风险清单（诚实版）

1. **提示词体量大，规则重复。** 实测 A 行业 19 个节点合计约 26.5 万字符，其中 01–04 每个约 2.5–3.4 万字符。规则词（「不写、不许、不能」等）每千字 2.5 到 7.3 个，审稿、开篇、分镜最密。「待确认占位」这一条在 `lib` 里 33 个文件、72 处出现。这是「规则太多」的直接证据。
2. **规则只加不删。** 过去每个问题都加一句规则。过滤多为黑名单（`SCENE_GEAR_RE`、`SCENE_TIME_RE`），每出现一个新词就要补一条，治标不治本。
3. **脚本页直接传账号定位原文。** 清单设计里脚本「不带定位」（`positioning: false`），但脚本页面把账号定位全文作为 `positioningContent` 传入，由 `extractScriptContext` 截出一段「脚本创作参考」。两者不一致，这段参考是无关信息的通道之一。
4. **知识库示例可被召回。** 知识库里的示例句（如「凌晨四点我来到市场的样子」）在检索命中时进入生成上下文。代码无法过滤知识库内容，只能收窄检索词，或在 Dify 侧处理。
5. **偏好学习可能学进具体细节。** 用户保存了一条含具体场景的生成内容，它可能被学成偏好，之后进入所有写稿板块。目前靠过滤兜底。
6. **自由对话读共用会话。** 对话需要延续，但它的回答会被后续问题带着走，是另一个潜在的串味通道。
7. **内容创作模板是死代码。** `lib/boards/script-query.ts` 第 654–731 行：第二个三元条件走到时 `isAd` 必为真，所以这段永远不会被执行。未删除。
8. **后检链路长，额外调用多。** 一次生成可能触发多次额外模型调用（条数复核、脚本修复、事实修正、细节核查、说话人检查、审稿校对等）。成本和延迟都会叠加。具体次数取决于内容，本报告未统计线上实际调用量。
9. **拆解的字数大。** 变现方向 JSON 的结构由模板决定（5 个方向 × 4 段 × 5 个字段，加 opening、emotion、shots），压缩需要改页面。
10. **测评覆盖有限。** 固定三个行业（川味餐饮、大码女装、家具）。它们不代表所有行业，也不代表所有人。
11. **Dify 工作流内部未核对。** 5 个知识检索节点的配置、模型选择、工作流内的提示词，都在 Dify 里，不在仓库里。
