## 产品经理已知问题

### T01（P0）：恢复失败仍显示 Failed to fetch，且不自动重试

**结论：确认。**

`components/workspace/CreationRestoreGate.tsx` 第 37–51 行请求 `/api/creation-sessions`。失败走第 51 行：

`catch (e) { if (!abort.signal.aborted) setError(e.message || '网络异常，请重试') }`

浏览器在连接被掐断时抛出的就是 `TypeError`，`message` 原文是 `Failed to fetch`。这个字符串被写进第 59 行的 `role="alert"`，不经过 `components/ui/feedback.tsx` 第 60–64 行的人话替换，也不经过 `lib/api-error.ts` 第 20–24 行的 `isNetworkError`。

`retry` 只在第 59 行按钮点击时加一，第 32–55 行的 effect 没有重试循环。同文件第 46 行对作品查询用了 `.catch(() => null)`，创作会话本身失败不会被吞掉，所以用户停在错误页，只能手点「重新恢复」。

生成请求已经有另一套处理：`lib/safe-post.ts` 对大 POST 做压缩和分块，`lib/api-error.ts` 第 36–43 行对秒失败重发一次。恢复门是后来加的入口，没有接上这套。

**修复：** 网络类错误换成 `NETWORK_ERROR_HINT`；对 `TypeError` 自动重试 2 次并退避，用户离开页面时的 `abort` 不要重试；按钮保留。补一条单测：`fetch` 第一次抛 `Failed to fetch`、第二次返回合法快照时，门应放行且界面不出现英文原文。

**改动面：** 小。一个组件加错误翻译和有限重试，再加测试。

### T02（P0）：部署时单实例重启，短暂 502

**结论：确认。** 本次没有登录生产机去打一次重启，空窗是部署脚本的结构决定的。

`同步到服务器.ps1` 第 307 行是 `pm2 restart xiaosong-web`。全文件没有第二个进程、没有 `pm2 reload`、没有换端口再切 Nginx。第 317–319 行自己写了：`pm2 restart` 返回后 Next.js 还要几十秒才起来。就绪循环在第 323–333 行才开始，而且探测的是服务器本机 `http://localhost:3000/`，不是 `/api/health`，也不经过对外的 Nginx。用户看到的 502 发生在「旧进程已死、新进程尚未 listen」这一段，脚本的等待盖不住这段。

机器内存约束写在第 84–90 行和第 204–206 行：物理内存 2G，明确不要删 `.next`，否则全量构建会把 SSH 和网站一起压死。所以不能靠「再起一个同样重的 Node」来假装有蓝绿，除非先量过两个 `next start` 的常驻内存。

`一键部署.ps1` 第 4–5 行承认同步后立刻访问会撞上重启窗口，然后第 89 行仍调用上面的脚本。`DEPLOYMENT.md` 从头到尾是 Vercel 自动发布，不提 PM2，也不能当现网手册。

仓库里已有 `/api/health`（`app/api/health/route.ts` 第 7–22 行）：进程在、数据库可读才返回 200。部署脚本没有用它。

**修复：** 短期在 Nginx 给 502/504 一个自动刷新的维护页，把空窗从「坏了」变成「正在发布」。中期在内存允许时换端口启动新进程，本机打 `/api/health` 成功后再让 Nginx 切换，然后停旧进程；切失败就停新进程，旧进程不动。2G 上若两个进程放不下，就维持单实例，但把空窗写进发布检查单，并避免在生成高峰重启。

**改动面：** 中。脚本和 Nginx 都要动，而且必须在那台 2G 的机器上量一次内存再定能不能双进程。

### T03：审稿框导入的是分镜表，而不是口播稿

**结论：确认。** 用当前 `lib/creation-flow.ts` 复现了三条路径。

审稿页只认交接里的 `scriptContent`（`app/dashboard/review/page.tsx` 第 122 行和第 135 行）。交接在 `buildCreationHandoff` 第 161 行：目标是审稿或分镜时，`scriptContent` 等于 `creationScript` 的结果。

`creationScript`（同文件第 85–110 行）的顺序是：

1. 来源是脚本或分镜时，先抓所有行首的「台词：」「口播：」。满 2 行就直接返回这些行（第 90–92 行），不再看「纯文字文案」。
2. 否则找标题里的「纯文字文案 / 口播全文 / 完整口播 / 完整脚本」（第 94 行）。「完整分镜脚本」对不上「完整脚本」，因为中间隔了「分镜」。
3. 小节结束只认「同级或更高级」标题（第 101–108 行）。`## 纯文字文案` 下面的 `### 分镜表` 不会结束这一节。
4. 找不到标题就整篇返回（第 98 行）。

复现结果：

- 分镜页生成的标准 Markdown 表（`lib/storyboard-standards.ts` 第 466–468 行那种「台词/旁白」列）送去审稿时，`scriptContent` 就是整张表。分镜的推荐下一步把审稿放在第一位（`lib/creation-flow.ts` 第 52 行）。`components/workspace/ResultPanel.tsx` 第 409 行把生成结果整份交给 `CreationLinks`，所以点「审稿优化」走的是分镜表，不是分镜页输入框里的口播。分镜页自己的「给这条起标题」按钮反而是对的：第 560–564 行带的是输入框里的 `scriptContent`。
- 脚本正文里「纯文字文案」是完整口播，分镜小节另有两行「台词：」。审稿框只得到那两句镜头台词，完整口播被丢掉。脚本页「审一遍」走的就是这条（`app/dashboard/script/page.tsx` 第 1411–1412 行）。
- 「纯文字文案」用二级标题、分镜表用三级标题时，表留在审稿正文里。

**修复：** 去审稿时只带口播。脚本结果优先用 `lib/script-copy.ts` 的 `extractPlainCopy`（第 23–49 行，认「纯文字文案」）。分镜结果不要把生成的表当待审稿，沿用分镜页输入框里的原稿，和「起标题」按钮同一份。行首「台词：」只能在没有纯文字文案时兜底，不能压过那一节。加三条回归：标准分镜表、台词行与口播不一致、二级标题包住三级表。

**改动面：** 小到中。规则集中在 `creationScript` / `buildCreationHandoff`，分镜页的继续创作要改成带原稿。

## 分维度说明

### 稳定性

做得好的部分：

- Dify 流断了会按会话和消息号取回全文。`lib/sse-stream.ts` 第 63–78 行把恢复等待放到 6 分钟，因为账号定位一类长文确实会写很久。服务端在 `app/api/dify/stream/route.ts` 第 531–547 行把半截结果换成全文。
- 大 POST 会被线路掐断。`lib/safe-post.ts` 第 15–17、48–65 行超过 6KB 先 gzip，再大就分块。
- 上下文溢出会清掉旧会话再请求一次（`app/api/dify/stream/route.ts` 第 507–528 行）。
- 生成有额度预占和并发槽，路由第 85–89 行要求每条结束路径都归还。
- 同一档案的创作窗口在单进程里排队（`lib/creation-window-lock.ts`）。

缺口：

- T01 的恢复门。
- 路由第 66 行 `maxDuration = 60`，后面的校对、事实修复、打磨使用 `AbortSignal.timeout(180_000)`（例如第 564、614、649 行）。自建 `next start` 不按 Vercel 的 `maxDuration` 杀请求，真正截断的是 Nginx 或代理的读超时。超时之后只能靠恢复逻辑，恢复失败用户就看到半截。
- 窗口锁在进程内存里，和单实例重启互相放大：重启既 502，也把队列清空。

### 安全

接口方面，抽查到的业务路由用 `requireUser`、`requireUserWithQuota` 或 `getUser()`。中间件 `middleware.ts` 第 32–33、91–114 行保护页面，不保护 `/api`，所以 API 必须自己鉴权。公开入口是注册、健康检查、保活、落地页统计、匿名漏斗、门票领取，能对上产品需要。定时任务用 `lib/cron-auth.ts` 第 8–12 行做长度和常量时间比较，密钥至少 16 位。

额度表的写权限已经从客户端拿掉（`supabase/migrations/20260922_rls_quotas_v2.sql` 第 39–47 行）。订单的新策略只允许未审核时改自己的行，但 P1-10 的旧策略名字没有被删除语句覆盖。
