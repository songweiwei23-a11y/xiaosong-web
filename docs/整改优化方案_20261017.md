## 二、整改方案

按「阶段」推进。每阶段做完，本地提交一次；**部署等你说「部署吧」**。

### 阶段 A：小改动，收益最快（预计 2～3 个工作日）

**A1 首页收敛成「一个主动作」**（对应 G3）
- 做法：首页顶部新增一张「下一步」主卡，内容由 `hooks/useSetupProgress.ts` 的建档、定位、简报三步状态决定（已有，直接复用）。其余卡片收进「更多」，默认收起。
- 新用户首屏：只有一个主按钮，比如「下一步：建档」。
- 有档案的用户首屏：「今天拍什么」（复用 TodayBoard）。
- 涉及文件：`app/dashboard/page.tsx`、`hooks/useSetupProgress.ts`。
- 验收：`tests/navigation-coverage.test.ts`、`tests/home-*.test.ts` 通过；新用户首屏可见的主动作只有一个。
- 需要你定：见决定 D1。

**A2 标题页、分镜页补「快速模式」**（对应 G2）
- 做法：照搬脚本页的做法：一个切换开关，快速模式只留核心选择（标题页留选题，分镜页留脚本），其余按档案和定位来。**默认关**，保持原来的行为。
- 涉及文件：`app/dashboard/title/page.tsx`、`app/dashboard/storyboard/page.tsx`。
- 验收：快速模式下请求体里只带必要字段；关闭时请求体与改动前一致（用快照测试锁住）。

**A3 生成前加「本次可用事实清单」**（对应 G1，这是最重要的一项）
- 做法：
  1. 从档案字段和已存素材里抽取结构化事实：价格、年限、数量、门店数、经历、已有的顾客反馈。
  2. 把清单作为一段固定文本放进所有写稿类提示词（复用 `lib/output-rules.ts` 的位置）。
  3. 规则写明：清单之外出现的价格、百分比、年限、经历，一律写成【待确认：xx】。
  4. 清单为空时，明确告诉模型「本次没有任何可用数字，所有数字都写占位」。
- 涉及文件：`lib/output-rules.ts`、`lib/creator-context.ts`（抽取清单），生成链路上的提示词拼接处（需要逐个板块核对，待核实）。
- 验收：
  - 单元测试：档案没有价格时，清单里没有价格字段。
  - **真模型探针**：用美甲那份档案跑一次选题和脚本，检查 88 元、188 元不再出现。探针要用真模型，会消耗 API 额度（见决定 D6）。
  - 夜间质检回归里「美甲选题」的 facts 项不再失败。
- 注意：这一条只能减少，不能保证为零。模型偶尔还会违反，所以结果页的「这几处请核对」保留，作为最后一道兜底。

**A4 把质检规则和用户侧组件对齐**（对应 G1 的验证）
- 做法：把夜间回归的 7 个用例，各自接上「用户侧组件」的检查（`FactCheckNotice` 用的 `runQualityChecks`、`TabooScan` 用的 `scanTaboos`），写成一组测试：同一段输入，用户侧一定能看到提示。
- 涉及文件：新增 `tests/user-visible-quality.test.ts`。
- 验收：这组测试全部通过，证明夜间回归发现的问题，用户在结果页上也能看到。

### 阶段 B：中等改动，需要先定设计（预计 4～5 个工作日）

**B1 发布后录数据：提醒 + 3 个数快速录入**（对应 G4）
- 做法：
  1. 作品标为「已发布」满 1 天、满 7 天，在首页出现「待录数据」卡，列出这些作品。
  2. 点开是一个小表单，只有 3 个必填数：播放、完播率、点赞；咨询、成交是可选项，不强制。
  3. 保存后写回 `works` 的 metrics 字段（字段已有，结构待核实）。
  4. 原来的「表格粘贴」和「表现复盘」保留，给喜欢批量录的人用。
- 涉及文件：`components/works/WorkCard.tsx`、新增 `components/works/QuickMetrics.tsx`、`app/dashboard/page.tsx`（待录数据卡）、`app/api/works/route.ts`（PUT 已支持 metrics，待核实）。
- 验收：录 3 个数不超过 20 秒（实际点按计时）；录完后作品卡立即显示数据；对应的待录数据卡消失。

**B2 学习进度可见**（对应 G5）
- 做法：在作品页顶部和首页学习卡上显示：「已有 X 条带数据的作品，再录 Y 条，学习会开始生效」。
- 口径：必须复用 `lib/verified-writing.ts` 里判断「有效样本」的同一个函数，不另起一套，否则页面显示和真实生效对不上。
- 涉及文件：`components/works/*`、`components/dashboard/LearningCard.tsx`。
- 验收：Y 的数字和后台学习统计里的样本数一致（用测试数据对一次）。

**B3 档案保存时的一致性检查**（对应 G6）
- 做法：写确定性的规则，不调模型，保存时只提示、不阻止：
  - 规则 1：选题方向或内容描述里出现「两个 / 双 / 两大 / 两个核心」，但经营品类（产品品类 + 赛道里的品类）数量 ≥ 3。
  - 规则 2：赛道和产品品类里同一个品类出现重复写法。
  - 规则 3：人设里的从业年限和经历里的年限对不上（只查数字明显冲突的情况）。
- 涉及文件：新增 `lib/profile-consistency.ts`，档案表单的保存处（待核实）。
- 验收：单元测试覆盖三条规则；用「川菜」那份档案的数据跑一遍，规则 1 必须触发。
- 注意：规则只能抓住这几类矛盾，不能保证全部。前采时的模型核对仍保留。

**B4 定位页：基于旧档案的提醒**（对应 G7）
- 做法：参考简报页现有的 `briefFactsChanged` 思路，给定位页也加一个「档案事实已改，这份定位是按旧档案写的」的提示。提示，不自动重写。
- 涉及文件：`app/dashboard/positioning/*`（待核实具体页面和字段）。
- 验收：改一项档案事实后，定位页出现提示；只改不影响事实的字段（如头像）时不出现。

## 三、怎么验证这套改动真的有用

1. **测试层**：每项都有对应测试；全量测试、类型检查、lint 无新增错误。
2. **生成质量**：A3 用真模型探针，前后各跑一次同一批档案，记录 88 元、最划算、唯一这类问题是否还出现。
3. **夜间回归**：服务器每晚 3 点的质检回归，看板上看 7 个用例里「未通过」的数量。目标：连续 3 个晚上，blocking 失败为 0。
4. **体验指标**（需要上线后才有数据）：
   - 新用户从建档到第一次生成的时间；
   - 作品「发布后 7 天内录入数据」的比例（B1 的目标）；
   - 首页主动作点击率。
   这些指标要先在后台能看到，否则无法判断有没有用。后台看板现状待核实。
5. **手机**：C2 的检查清单，由你完成。
