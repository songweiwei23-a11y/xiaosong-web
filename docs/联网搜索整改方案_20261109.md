# 开物联网搜索整改方案（2026-11-09）

目标：问「今天、这两天、本周」的事，能搜到当天、当周真实发生的信息，带日期和链接；搜不到就直说，不拿旧闻、无关页凑数。

---

## 一、现在用的是什么

| 项 | 现状 |
|---|---|
| 搜索引擎 | 阿里云 OpenSearch「联网搜索」（服务 `ops-web-search-001`），只有这一家，没有备用 |
| 调用方式 | `way: pro-fetch`（增强搜索 + 深度解析网页正文），`top_k` 10 / 6，关闭改写 |
| 在哪用 | 只在**自由对话、开物助理、深度研究**里用。选题、方向等创作板块不联网，热点只靠服务器直读的抖音热榜 |
| 一次提问的流程 | ① 小模型读懂需求、写搜索计划（意图、1～2 个搜索词、时效、关键词）<br>② 同时发：1～2 次通用搜索 + 最多 4 次定向搜索（地方官网、热榜官网、官方站点，用 `site:`）<br>③ 本地过滤挑 6 条（去天气、行情、导流页，按地名、时效、相关度）<br>④ 补读前 3 条网页正文（每条 5 秒）<br>⑤ 最多 3.2 万字交给 Dify 写回答 |
| 额度 | 会员联网额度，一轮记一次；阿里云按次计费 |

## 二、为什么质量差（按影响排序）

1. **时间过滤没交给搜索引擎做。** 阿里云接口自带 `time_range`（day / week / month / year），我们没传。现在是先把不分时间的结果搜回来，再在本地按日期丢掉旧的。新内容本来就没被搜回来，所以问「今天的热点」时，要么拿到旧闻，要么丢完了说「没找到」。这是「实时性差」的头号原因。
2. **并发超过接口上限，多出的几路被悄悄丢掉。** 这个接口全账号每秒最多 3 次调用（官方文档写明），我们一个问题同时发最多 5 次，深度研究、开物助理也共用这个上限。超出的那几路会被限流；定向搜索失败在代码里是「忽略那一路」，所以地方新闻、热榜那几路很可能经常白搜，没人知道。
   - 这一条是读代码加读文档推断的，**要用阶段 0 的实测确认**。
3. **用搜索引擎去搜热榜。** 热榜是实时页面，搜索引擎里存的是几天前的快照。抖音热榜已经改成服务器直读了；微博、百度、头条还是用 `site:` 去搜，拿到的多半是过期的。
4. **只有一个引擎。** 阿里这个接口是给大模型补知识用的通用搜索，不是新闻实时引擎；中文本地新闻、社交平台内容覆盖有限，出问题时没有备用。
5. **正文读得太浅。** 只补读前 3 条，每条 5 秒；公众号、知乎、小红书、抖音这类页面基本读不到，模型手里大多只有几行摘要，回答就空泛。
6. **没用「多轮多源」增强搜索。** 接口有 `extend_search`（复杂问题约 7 秒），对找案例、找数据这类长尾问题更全，我们没开。
7. **创作板块不联网。** 选题、创作方向想蹭当天的新闻热点，只能靠抖音热榜，看不到行业新闻、本地新闻。
8. **没有质量监控。** 每晚质检不测联网，哪天坏了、变差了没人知道；每一路搜索成功、限流还是超时，也没有记录。

## 三、整改目标（验收口径）

- **时效类问题**（今天、这两天、本周）：最后挑出的来源里，至少 80% 落在要求的时间范围内，每条都带日期。
- **热榜**（微博、百度、抖音、头条）：数据不超过 10 分钟前。
- **固定评测集 20 问**（新闻热点、本地新闻、平台规则、行业数据、同行案例各 4 问）：每晚跑，看这几项：相关来源数、新鲜度、正文能读到的比例、回答里的引用对不对得上来源。
- **失败不再静默**：每一路搜索的结果（成功、限流、超时、0 条）都记日志，后台能看到。

## 四、分阶段做

### 阶段 0　实测基线（先做，需要你批）
- **做什么：** 在服务器上用固定 20 问跑现在的流程，记录每一路搜索的状态（有没有被限流）、结果日期分布、正文长度、网页能不能读到、最后挑了哪些。
- **成本：** 约 40 次阿里云搜索 + 20 次小模型调用，不调 Dify，不碰用户数据。
- **产出：** 一张基线表。后面每一步都和它比，确认真的变好了。

### 阶段 1　把现有接入用对（不换引擎，成本最低，见效最快）
1. **时间过滤交给引擎：** 搜索计划里的时效换算成 `time_range`（今天、昨天 → day；本周 → week；最近一个月 → month）。按时间搜不到时，再放宽一档补搜一次，并在回答里写明「当天没找到，以下是本周的」。
2. **按上限排队：** 所有搜索走同一个队列，每秒不超过 3 次（开物助理、深度研究也走它）；被限流的那一路等一下重试一次，不再直接丢掉。
3. **长尾问题开增强搜索：** 案例、数据、做法类问题开 `extend_search`。
4. **读深一点：** 补读前 5 条，每条超时 8 秒；读不到的标明「只有摘要」，提醒模型别过度解读。
5. **每一路都记日志：** 状态、耗时、条数，后台监控页能看到。

### 阶段 2　热榜直接读，不靠搜索
- 微博、百度、今日头条热榜，和抖音一样由服务器直接读公开榜单，10 分钟全站缓存。
- 只读公开榜单页，不登录、不碰 Cookie、低频缓存（和抖音热榜同一套规矩）。
- 问「热点、热搜、最近什么火」时，热榜作为第一手来源，搜索只用来补每条热点的来龙去脉。

### 阶段 3　加第二个搜索引擎，互为补充
- **候选**（都是国内接口，都支持「一天内」的时间过滤）：
  - **智谱 Web Search：** 可选智谱自己的引擎，或搜狗、夸克的引擎。
  - **博查 Web Search：** 时间过滤可到一天内，也支持指定日期范围。
  - **百度千帆 AI 搜索：** 时间过滤是周、月这一级；参数要以官方文档为准，我查到的说法不一致。
- **选法：** 用阶段 0 的 20 问，把阿里加候选几家放在同一时段对比：新鲜度、相关度、能读到的正文、价格。选 1 家和阿里一起用。
- **合并方式：** 两家同时搜，去重后按「时间 + 相关度」排序；一家挂了另一家顶上。
- **需要你做：** 注册选中那家、拿到密钥。我不能替你开账户。密钥粘到后台「联网搜索密钥」页，先真搜一次验证通过才保存（和现在一样）。

### 阶段 4　创作板块接上实时热点（可选，要单独验证）
- 选题、创作方向页加一个「结合今日热点」开关。打开后拉热榜和行业、本地新闻，作为可选素材交给模型；关着就和现在一样。
- **风险：** 热点可能把选题带偏、偏离账号定位（和「已经做过」清单把模型带到旧题上是同一类问题）。上线前要做带热点和不带热点的真实模型对照，两个行业。

### 阶段 5　每晚监控
- 每晚质检加联网 10 问（从评测集里轮换），指标存进后台。连续两天下降、或某一路限流比例过高，就发告警。

## 五、成本和风险

| 项 | 说明 |
|---|---|
| 阿里云搜索 | 阶段 1 开了按时间补搜和增强搜索，每个问题的调用次数大致持平到略增（排队后限流白搜的会变少）。`pro-fetch` 按 pro + pro-fetch 两项计费 |
| 第二引擎 | 按次计费，价格开户时到对方官网确认；可以只在时效类问题上启用，控制成本 |
| 热榜直读 | 几乎不花钱；风险是平台改了页面就读不到，要有监控和降级（读不到时回退到搜索并标明） |
| 速度 | 排队加补搜，最慢的问题可能多 2～5 秒；网页补读是并行的 |
| 不变的 | 用户联网额度的口径不变（一轮记一次）；搜不到就直说、不编来源的规则不变 |

## 六、要你拍板的事

1. 批不批阶段 0 的实测（服务器上跑，约 40 次阿里云 + 20 次小模型）。
2. 阶段 1、2 实测后直接做吗？这两步不换引擎、不加钱，主要是把现有的用对。
3. 第二引擎要不要做？要做的话，候选三家先一起对比，还是你已有倾向的一家。
4. 创作板块要不要接实时热点（阶段 4）？
