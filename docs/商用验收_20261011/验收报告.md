# 开物模型输出商用验收（2026-10-11）

本报告只找问题，不修改代码。

## 一、验收标准

**硬性门槛**（任一不过，该条输出不可商用，无论其他分数多高）：

| 编号 | 门槛 | 判定 |
|---|---|---|
| G1 | 无编造事实 | 价格、百分比、倍数、销量、顾客证言、个人经历、店内做法/菜单、数据来源，凡档案和素材里没有依据、又没有标【待确认】或 X 占位，就不过 |
| G2 | 交付完整 | 交付物齐全，无截断、无拒答、无空节（如审稿缺优化稿） |
| G3 | 平台合规 | 无绝对化用语（最、第一、全城、100%、保证）、无站外引流（加微信、私信）、无操纵数据（刷评论、小号、买赞）、无禁用词（揭秘） |
| G4 | 遵循设定 | 编导设的时长、数量、目的、人称、主题不被改写 |
| G5 | 无内部泄漏 | 不出现自检块、校对过程、提示词痕迹、内部标签（如「起号36计」）给观众看 |

**质量评分**（满分 100，门槛全过后才有意义）：可用性 30、专业与具体 20、贴合档案与意图 20、表达 15、稳定性 15。

**结论档位**：商用可用 = 五个门槛全过，且评分 ≥ 80，且多轮一致；有条件可用 = 门槛全过但评分 70–79；不可商用 = 任一门槛不过，或评分 < 70。

## 二、覆盖范围

本次验收基于同一个真实账号（锦园地摊串串一元火锅），真实路由、真实模型，共覆盖以下板块的输出：

| 板块 | 样本 | 来源 |
|---|---|---|
| 标题封面 | 3 轮 × 2 次（修复前后） | 评测 |
| 脚本生成 | 3 轮 + 显式 30 秒 2 轮 + AI 推荐 2 轮 | 评测 |
| 选题策划 | 3 轮 × 2 次 | 评测 |
| 审稿优化 | 3 轮 × 2 次 | 评测 |
| 跨行业二创 | 3 轮 × 2 次 | 评测 |
| 陷阱（无价格引流脚本） | 3 轮 × 2 次 | 评测 |
| 开篇钩子 | 线上记录 + 2 轮修复后 | 线上与评测 |
| 创作方向 | 线上记录 + 2 轮修复后 | 线上与评测 |

**未覆盖**：账号定位、起号方案、内容规划、创作简报、拆解爆款、高阶自由对话（自由对话走另一条接口，且是用户用得最多的板块之一）。这些必须下一轮补测，本报告不对它们下结论。

## 四、问题清单（按严重程度）

### P1 编造事实：最严重，所有内容板块都有

证据（都在 `.tmp/quality-eval/out/`）：

- **比例与对比**：选题 r3「十个客人九个加单」；成交理由 r1「同样的量在别处要贵一倍」；二创 r3「十个人有九个」。这些数字档案里没有，也没有标【示例】。
- **经营做法**：成交理由 r1「地摊卖不完不过夜，进的都是当天能卖完的量」、r2「串串都是当天穿，不过夜」；脚本 r2「我早上五点熬的牛油底料」；脚本 r3「签子按颜色明码标价」「锅底免费给你加汤」。
- **顾客证言与故事**：选题 r1「师傅说有个客人每次只点白水锅底」「客人说我就看看不点，当场下单」；选题 r2「有个客人说你们家火锅没海底捞好…成了每周来三次的老客」；陷阱 r2「周围上班的…不少人一周来好几次」；陷阱 r3「来过的人都说，这个价位能吃成这样，值了」。
- **个人经历**：开篇候选「昨天我在棚外站了两分钟，冻得直哆嗦」（带风险提示，但未用假设语气）。

根因（我的判断）：

1. 提示词已经明令「没有依据用【待确认】」，模型仍然违反，说明只靠提示词约束不够。
2. 服务端的出处检查（`unsupportedFacts`）覆盖的是价格、证言、经营做法等固定句式，对「比例」「经历」「客人故事」的覆盖不全，漏掉的比命中的多。
3. 修正只做一次，修正稿仍可能留下漏网的编造。

### P2 选题板块整体不可商用

- 每条选题都讲一个客人或师傅的故事，题材高度同质，多条只是换了说法。
- 「起号36计」「第31计」这类内部标签直接出现在给观众看的选题文字里。
- 只有 3/10 左右的条目能不改直接用，其余需要编导重写。
- 修复后数量正确（10 条），但质量没有实质提高。

### P3 审稿板块：拒答与空交付

- 3 轮中有 1 轮仍写「本轮未提供档案，无法核对」，优化稿是占位。
- 另外 1 轮把中段整段删掉，30 秒稿只剩两句台词，可用性很低。
- 评分前后矛盾（同一份报告里出现「合计 25」和「实际给分 35」）。
- 根因之一：这个档案的人设事实卡为空，审稿没有年限等依据可对照；代码侧的「不得以缺档案为由拒答」规则只部分生效。

### P4 成交理由：结构好，但经营做法与比例全靠编

- 17 条判断的结构和拍法很好，但每一条「怎么拍」里都混着未核实的经营细节。
- 「同样的量在别处要贵一倍」这类对比没有任何素材支撑，直接可以在视频里说出来，风险很高。

### P5 脚本：口播可用性低，且 AI 推荐版偏长

- 显式 30 秒的口播已经降到 142–150 字，符合时长。
- AI 推荐版口播 321–568 字，分镜 12 个镜头、175 秒。按口径是「偏长没关系」，但观众未必愿意看，商用上需要编导再缩。
- 口播里大量【待确认】占位（「【按现场真实回答】」「【待确认：几片】」），直接念不了，需要编导先补素材。这是为了不编造而付出的代价，但商用体验差。
- 第 4 步曾出现「小号预埋评论」（已堵住，见 `eafb144`）。

### P6 内部术语与元信息泄漏

- 选题中出现「起号36计·第31计」「小黄脚本结构」等内部术语。
- 脚本和选题末尾仍有「拍摄要点」「待老板确认」「数据预期与迭代方向」等说明块，有些是有用的，但混在交付稿里，不易区分哪段能直接发。
- 开篇候选的「为什么抓得住这群人」「风险」是给编导看的，而不是给观众的，需要明确分开。

### P7 平台合规与夸张承诺

- 标题「俩人吃不完」「学生党吃撑」「一元火锅能吃饱吗」等属于宣传式承诺，档案里没有「吃撑」的依据。
- 「全城最正宗」「最正宗」已在审稿里被识别，但在选题和标题里仍会出现。
- 禁用词「揭秘」已替换，但替换之后仍可能有「拆解」之外的类似表述（如「内幕」）未被检查。

### P8 档案依赖：这个档案的数据不全

- 人设事实卡为空，禁忌设置为空。审稿、事实检查都缺少对照物，这是 P1、P3 的重要外部原因。
- 建议用户补全人设事实卡（出镜人、年限、来店时长、店龄）。这一步只能用户自己做。

### P9 速度与稳定性

- 首字延迟中位 8 秒，可接受。
- 总耗时中位约 58 秒，审稿和二创 100–130 秒，偏慢。
- 同一输入多轮之间质量波动大（如脚本 r1 83 分、r3 69 分），稳定性不足，商用需要减少这种波动。

### P10 覆盖缺口

- 账号定位、起号方案、内容规划、创作简报、拆解爆款、高阶自由对话都未纳入本次验收。自由对话尤其需要单独测，它是用户用得最多的入口之一。

## 五、和前几轮修复的关系

- **已修**：开篇人称、创作方向季节、整批与拆解误读标签、完整目的丢失、显式时长超长、小号预埋评论、顾客证言部分检测、禁用词「揭秘」。
- **部分修**：编造事实（修复后仍在约 1/3 的样本中出现，见 P1）；审稿拒答（见 P3）。
- **未修**：选题质量（P2）、成交理由的经营细节（P4）、元信息与术语（P6）、覆盖缺口（P10）。

## 六、建议的下一步（待你确认后再做）

1. 先补测账号定位、起号方案、高阶自由对话，确认是否还有未知问题。
2. 选题：重写提示词，禁止「客人/师傅说过某件事」的故事型题目，把题目拆成「可拍的动作/对比/问题」，并去掉内部术语。
3. 编造事实：把出处检查扩展到比例、经历、客人故事、经营做法，修正改为最多两轮，修正后仍不过门槛的直接降级为【待确认】版本交付。
4. 审稿：档案无事实卡时强制走「按原稿与账号背景核对」路径，去掉拒答分支。
5. 成交理由：只输出判断和拍法，经营细节一律改成【待确认】占位。
6. 脚本：AI 推荐版增加口播字数的软上限提示，并把说明块与口播分开输出。
7. 请你补全档案的人设事实卡。

原始输出和评分都在 `.tmp/quality-eval/out/` 与 `.tmp/quality-eval/scores.json`。
