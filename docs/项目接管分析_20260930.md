## 2. 产品目标和用户重视的方向

项目现在的品牌是“开物”，早期称“小宋编导工作台”。名字取自《天工开物》，强调创作和打磨。

目标用户主要是短视频编导、代运营及实体商家，餐饮是首页示范场景。用户长期目标是面向编导代运营的强创作助手；当前实现是由人选择、审核和推进的 AI 工作台，尚未形成自动发布、自动追踪真实经营结果的自主运营闭环。

历史需求反复强调：

1. 输出要理解真实客户的行业、生意、人设、观众和拍摄条件，不能只是照搬档案或凭空编经历。
2. 小黄的起号打法与薛老师的四大脚本体系都要做好，用户自由选择；不是强制所有任务使用同一种模板。
3. 流量型、人设型、变现型是视频的目的，教知识、晒过程、聊观点、讲故事是内容形式，两者不可混为一谈。
4. 所有创作成果要能保存、重新打开、继续创作，板块之间能交接；不同客户档案要隔离。
5. 界面要简单、干净、精细，有毛玻璃质感，尤其重视结果区、历史区和移动端；重大视觉方向通常先提供可选方案。
6. 首页要让小白愿意尝试，后台数字和权限操作要真实；内链不能指向不存在的页面。
7. 全程使用中文解释。最新约定是先汇报问题，由用户判断是否修改。

这些是从历史需求提炼出的产品方向；旧会话中的部署许可或数据操作许可不自动延伸为本轮许可。

## 4. 技术架构与真实工作链路

实际安装的是 Next.js 16.3.0，使用 App Router、TypeScript、React 18、Tailwind 3、Radix/shadcn 风格组件。Supabase 提供认证、PostgreSQL 和文件存储；Dify 提供知识检索、模型调用、对话及文件能力。

核心生成路径：

`用户选择当前档案 → 页面读取档案/定位/简报/成交理由 → 按任务组装提示词 → 服务端认证和额度检查 → Dify 的知识检索、联网及模型 → SSE 返回 → 服务端登记用量 → 页面保存结果及作品关系`

需要区分两层提示词：

- 网站各板块的业务规则主要在 `lib/*-standards.ts`、`lib/remix.ts`、`lib/viral-breakdown.ts` 等模块，以及页面组装代码中。
- Dify 通用提示词在 `docs/dify/system-prompt.md`，工作流文件仍沿用旧文件名 `docs/dify/小宋编导文案工作台.yml`；文件内应用名已是“开物”。

保存的 Dify DSL 使用 advanced-chat，主模型名为 `claude-sonnet-4-6`，有五个知识检索节点和 Tavily 搜索；检索配置包括 BAAI/bge-m3 向量化、bge-reranker-v2-m3 重排。这里的模型配置与负责开发的 Claude 客户端不是同一概念。DSL 代表本地保存状态，线上是否仍一致本轮未验证。

五个知识专题是定位与选题、脚本与文案、拍摄与执行、综合手册、成交理由与实战；本地整理的 Markdown 位于 `编导知识大全/_导入Dify/`。原始课件多数被 Git 忽略，不能仅凭 Git 仓库恢复全部原始素材。

部署脚本指向腾讯云 Ubuntu，历史路径为 `/var/www/xiaosong-web`，PM2 应用为 `xiaosong-web`，Nginx 转发 Next 服务。同步流程为打包源码、上传、安装依赖、后台构建、重启、等待可响应、源码哈希比对。本轮只检查脚本和历史，没有登录服务器确认当前状态。

网站源码、数据库结构、Dify 工作流/知识库是三个独立变更面。同步网站脚本不等于已执行 SQL 或发布 Dify 工作流。

当前仍有部分“记忆”的边界不一致，见问题清单。会话持久化、结果恢复、档案背景和页面交接应分别验收，不能用一句“有记忆”替代四种检查。

## 10. 从历史故障继承的排查经验

- “源码已上传”不等于“新版本在服务”：曾出现 PM2 工作目录或旧构建不一致，以及后台构建未真正启动却被判为成功。需要确认实际进程目录、构建完成标志、服务就绪和源码一致性。
- Dify 历史上因重导入/切换应用导致 key 变化；先确认调用的是“开物”及 key 有效，再判断提示词问题。不能在报告中打印 key。
- 大图曾超出 Dify 云端模型调用 5MB 限制；base64 会增加体积，工作流曾把图重复注入。现有客户端将截图预算压到约 1.6MB，并有缩图重试；需要用难压缩素材验收。本轮未重新调用线上验证。
- “Failed to fetch”要先对照服务器访问日志；历史上大 POST 被网络链路掐断。优先让原文留服务端、只传 ID；收费生成不能无条件自动重试，避免重复调用。
- 不在 dev 运行时删除 `.next/dev/types`。历史上会导致本地 API 全 404；不能把开发缓存问题误当业务接口问题。
- 不报错但没有作用的功能是长期问题：旧链接、未注入的知识、假数字、没取回来的历史。扫描要自证扫到了真实内容，并辅以行为验收。
- 不应为了验证去改真实用户额度或删除数据；历史记录中的一次失误不能作为未来可重复操作的范例。

## 11. 两位助手共同维护的建议（尚未修改项目规则）

可以共同接管，但应让协作落在可追溯的变更上：

1. 每项需求明确一位实施者、另一位审核者。产品方法论与结果质量、代码与稳定性可互相审核，不强制永久分工。
2. 同时开发使用各自分支和独立工作目录；不要让两位助手同时编辑当前同一个工作区、提交对方未完成文件或共享一个开发缓存。
3. 共享本文及一份后续变更记录，写清需求、改动、测试结果、SQL/Dify 依赖、未完成项。双方先读记录和 Git 状态再开始工作。
4. 同一轮发布由一位助手负责；先合并和验收，再按用户决定发布，避免一方部署另一方的半成品。
5. 问题、修复建议和实际已完成事项分开记录；本轮优先执行用户“先汇报、我判断”的要求。

当前适合接管的起点是：保留现有 Claude 工作区，用户确定问题处理顺序，再由一位助手完成该轮收尾、另一位复核。无需重做已有功能，也不应依据过时说明整体重写。
