# 开物问题成因与优化实施方案

日期：2026-10-05。依据同目录《开物体验与产出质量深度研究报告》、13次正式模型样题、一次研究分节试验和当前关键代码核验。本文件是分析与实施建议，没有修改业务代码、数据库、Dify设置或正式网站。

## 判断原则

现有证据把主要问题指向“事实约束、资料选择、任务规则、生成后验证”之间的衔接。模型能够完成许多任务，但系统对输出的约束与验证还不够可靠。不能仅凭这些样题断言模型供应商不真实、温度0.5不合理或阿里云搜索整体质量差。

下文区分：

- **已确认**：代码、配置或本轮实际输出直接支持。
- **可能贡献因素**：有机制解释，但需要对照试验才能量化影响。
- **尚未验证**：需要补测，不应写成既定故障。

## 1. 编造数据、顾客故事和经营承诺

### 原因

已确认：样题出现未提供的“90%”“很多客人说”、案例尺寸、价格、顾客经历和可提供的福利。已有“不编造”提示词及部分事实校验，但它们没有稳定阻止上述输出。

当前事实检查把档案及原稿中的数字汇总成一个集合，没有完全按“对象—属性—单位”判断。离线复现中，“老板从业38年”可以让“产品38元”不触发价格警告。百分比识别也依赖“据统计”等词，普通“90%的业主……”没有被识别为统计断言。事实检查只覆盖部分任务，并依赖档案存在，不能当作全部产出的统一保障。

可能贡献因素：提示词同时要求具体场景、人物、金句、拍摄动作和完整交稿，而没有把“缺失事实时允许输出什么”规定得足够明确。模型容易以合理化补充满足模板。需要删除或替换案例的对照试验才能确认影响大小。

### 解决与优化

1. 建立统一事实表：实体、属性、值、单位、来源、确认状态。把“从业年限”“本地经营年限”“门店成立年限”作为不同属性。
2. 区分已确认事实、创作建议和虚构示例。允许创作虚构案例，但明确标识；真实商家稿不得把虚构示例写成真实顾客见证。
3. 缺失数据优先采用不依赖数字的表达。只有影响核心内容的事实才请求用户补充，避免把每次创作变成填写长表。
4. 统一检查各板块中的对外事实，不仅检查脚本；检查价格、占比、时间、人物经历和经营承诺的语义归属。
5. 对重要的不支持断言标出位置，执行受限修订后再检查，不能依靠模型一句“自检通过”结束。

### 验收

固定测试“38年/38元”“5年从业/杭州2年”“无价格/生成报价”“无顾客故事/生成见证”“无统计/百分比”。发布门槛是这些已定义用例通过，多次生成仍正确。它不能证明开放世界中永远不会编造。

## 2. 联网成功，但来源判断和结论仍会错

### 原因

已确认：W1搜索节点成功，但回答把非官方网页称为Dify官方资料，并混淆LLM会话历史与其他记忆机制。另一次研究分节采取搜索加页面读取后更谨慎，但仍没有找到直接回答问题的LLM说明页。

搜索请求主要是query、top_k、mainText和lite模式，当前所读请求代码没有权威域名筛选。搜索结果格式化已有错误处理、合法URL检查和“不执行网页指令”的约束，但没有建立每个重要结论与原文证据的对应关系。“接口返回结果”与“资料足以证明答案”是两个验收环节。

不能从一次检索失败推断阿里云服务整体不佳；查询构造、选页、阅读范围和模型解释共同影响结果。

### 解决与优化

1. 按问题类型选择来源：产品参数和软件行为优先官方说明；时效性问题保留资料日期、适用版本。
2. 查阅直接回答问题的页面，不仅使用搜索摘要或前两条结果。资料不足时有限次数改写查询，设置搜索与阅读的预算上限。
3. 建立“结论—支持段落—链接”的证据对应关系。没有证据的结论标注待确认或推断，遇到冲突明确呈现。
4. 单独校验“官方”称谓、域名与结论支持关系，不能仅检查链接能否打开。
5. 保留已有会员限额；内部重试也要计入服务成本监测，避免单次会员联网请求无限扩张。

### 验收

重跑W1，准确区分节点会话历史、会话变量与跨会话持久化，且引用真正支持该结论的官方页面。补充“来源冲突”“找不到资料”“旧版本资料”三类用例。

官方依据：[Dify LLM节点说明](https://docs.dify.ai/en/cloud/use-dify/nodes/llm)。

## 3. 质检和高分给出过强的可信感

### 原因

已确认：部分输出含编造内容，却同时宣称“无编造数据”。项目原生审稿样题R2经过实际正文提取后，规则检查仍通过；这里不存在本轮评估器最初重复提取正文所造成的产品解析故障。

`quality-checks.ts`中的事实和禁忌判断仍有词形规则局限：“挂衣区”会被误识别成地名，“打开到最大角度”会被普通禁忌规则误报。“任何一条链接”也不能证明全文所有统计数据都有来源。

`quality-checker.ts`主要看结构、关键词、时间标记等，再映射成分数和“MCN级”等评价。这可以衡量部分模板符合程度，但没有专业编导盲评或真实使用效果的校准。模型自身的评分与程序评分还需分别看待，不能混成一个可靠总分。

### 解决与优化

- 分开展示结构检查、事实检查、来源检查、可拍摄性和人工待确认项。
- 将“全局自检通过”改为具体的“哪些项目检查通过，哪些仍需核对”。
- 用上下文区分地名、动作和修辞；统计来源绑定具体断言。
- 客观规则负责计算和硬约束，独立语义评估负责遗漏与矛盾，人工负责专业质量校准。
- 未校准前不把格式分数包装成行业等级或发布效果保证。

### 验收

以上四类误判均纳入回归。盲评中比较程序检查、语义评估和两位评审的判断，记录漏报、误报及分歧，而不是只统计“通过了多少项测试”。

## 4. 简单任务也负担很重，部分结果等待较长

### 原因

已确认：本轮13次任务均调用五组知识检索，每组返回四条；Excel公式和局部改写也不例外。输入约2.8万至3.6万token，本地系统提示词约8169字符。样本首段内容中位数约7.5秒、完成中位数约22.6秒，最长约61.9秒。

固定检索和长提示词很可能增加输入、等待和干扰，但本轮未做去掉检索的对照试验，不能承诺改完快几倍。长回答本身也影响完成时间。模型供应商的实际计费、缓存及最终接受参数尚未独立核验，Dify显示价格0不能当作免费。

### 解决与优化

1. 按任务路由资料：公式、局部改写等默认不走编导知识库；审稿、选题、脚本只查有关的资料，资料不足才扩大检索。
2. 对片段去重，控制总长度，设置与数据集相适应的相关性阈值；不存在一个适用所有资料的万能阈值。
3. 将通用提示词拆成公共规则和任务规则，减少当前任务不需要的约束。
4. 为短回答、脚本、研究分别校准输出预算；不能以统一50000上限代替任务规划。
5. 用阶段状态让用户理解等待过程，保留流式输出与已有取消、恢复机制。

### 验收

同题同模型对照原流程与新流程，比较输入量、实际账单、首段与完成耗时、事实正确性及人工可用率。补足代表性网络和并发样本后再报告p95，不能拿当前13题作为SLA。

官方依据：[Dify知识检索节点](https://docs.dify.ai/en/cloud/use-dify/nodes/knowledge-retrieval)。

## 5. 参数没有按任务验证，用户短要求可能输给模板

### 原因

已确认的代码风险：脚本页根据补充要求是否超过100字改变优先级；短要求分支写了“MCN标准优先于用户补充要求”。但“别改正文，只换开头”即使很短，也应拥有明确的约束地位。这个风险不代表所有局部改写都失败，本轮C1就成功保留了任务范围。

参数方面，本地2026-10-02导出是temperature0.5、top_p0.9、输出上限50000、记忆窗口20。当前正式运行确认了模型标识，但未重新导出控制台完整发布配置，因此这些参数不能一概视为已重新核实的正式值。现有值缺少分任务对照验证；没有证据将错误直接归因于0.5。

### 解决与优化

- 统一优先级：已确认事实和安全边界、用户明确约束、当前创作目的、任务模板。明确约束不按字数决定效力。
- 局部改写锁定修改范围；事实提取和审稿优先稳定，方案发散允许更多差异，但都遵守事实约束。
- 按任务逐项试验参数，保持其他条件不变；先评估结果，再确定数值。
- 保存并核对正式发布配置及版本，避免本地导出、控制台草稿和正式API不一致。

### 验收

短要求、长要求、互相冲突的历史要求、只改选中段落均纳入用例。检查输出是否真正遵守，而不是只检查提示词包含了优先级文字。

## 6. 板块互通已有基础，长期承接仍可能漂移

### 原因

已确认：已有原始内容、当前内容、设置、任务承接和保留规则。本轮脚本转分镜保留了主要方向，但上一环节产生的无依据事实也会一起传下去。

自动配置仍包括文本解析和默认项，不能证明已选到“最佳选项”。交接入口包含sessionStorage临时消息；提示词中的历史引用是最近8条、每条最多1200字符，模型窗口20也不等于永久读取全部历史。这些上下文限制不代表数据库历史被删除；当前代码不能沿用旧的“500条就截断存储”说法。

### 解决与优化

1. 建立持久化创作简报：目标、人群、事实、方向、结构、语气、时长、平台、行动指令、禁止修改项。
2. 每个字段保留来源，区分用户确认、系统推断、模型建议。关键事实继承；仅在用户授权改变方向时更新。
3. 以作品或创作任务ID跨页面、跨设备恢复，交接内容入库，临时消息用于触发页面接收。
4. 各模块先根据简报预填，再做适用性检查；信息足够就一键生成，核心矛盾才请求确认。
5. 支持分支创作、方案比较、局部替换与回到父版本，保持事实一致，让可玩性来自表达差异。
6. 下游先检查继承材料的事实状态，避免连续创作放大上游错误。

### 验收

审稿→开篇→脚本→分镜，选题→脚本→标题，自由对话→审稿等路径，检查目标、人群、年限、价格和保留要求；补测刷新、隔天恢复、多标签、换设备、切档案和旧版本继续创作。

## 7. 标出的时长不等于真实可拍时长；附件效果缺专项证据

### 原因

已确认：分镜样题在5秒内安排46个汉字和展示动作，却宣称整体能在28—30秒完成。时间标记是模型规划值，缺少语速、停顿和动作预算的计算或实际朗读核验。

视频目前通过抽帧与拼图提供画面，模型并非逐帧观看原始视频；抽样、压缩和缺失的音频线索可能影响理解。六附件发布参数已经核对，但本轮没有新增复杂扫描件、低清图片、跨页表格和动态视频的识别基准，不能把这些风险写成已证实的准确率故障。

### 解决与优化

- 按镜头计算口播字数、语速、停顿和动作时间，冲突时缩稿或延长，不只改时间标签。
- 支持朗读预览或实测时长；初期估算明确标为估算。
- 视频结合字幕、音频转写和场景变化抽帧，并引用时间点；低清或覆盖不全时说明局限。
- 为附件建立专项样题，识别失败给出具体补救提示。

### 验收

用真人朗读或选定配音速度核对时长；附件分别统计文字、表格、事实提取及画面线索的正确性。不要用“能上传”代替“识别准确”。

## 8. 稳定性与质量缺少持续、独立的验证闭环

### 原因

本轮13次调用均完成，没有复现当前API故障；样本不能证明长期稳定。工程测试主要验证逻辑和契约，不等于稿件真实性、用户满意度或发布效果。多行业试题还有档案字段继承等混杂因素，需要独立、干净的测试档案。

已确认IP入口仍为HTTP，但这不能推断所有其他域名都没有HTTPS。已有失败恢复、配额和历史机制应先验收，避免无依据地重写。历史重启次数也不能直接用来推断当前故障频率。

### 解决与优化

1. 建立30—50个覆盖行业、任务、难度和边界的固定样题，关键题每配置至少重复3次；每轮根据成本和变更范围选子集。
2. 事实、来源、数学和承接用可核对标准；创意、口吻、可拍性用独立编导盲评。
3. 检查断流、弱网、刷新、取消、重复点击、并发与数据库慢响应；验收结果、历史和扣费的一致性。
4. 正式访问入口启用HTTPS并验证跳转及登录状态。
5. 在用户允许的反馈中记录稿件采用率、修改位置、连续创作完成率与失败原因；生成量、复制量和视频播放量不能混为同一质量指标。

官方评测依据：[Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## 实施顺序与依赖

| 阶段 | 重点 | 发布门槛 |
|---|---|---|
| 第一阶段 | 修正短要求优先级，统一事实表，修复已复现质检误判，联网结论绑定证据 | 已知错误样题多次通过；正常创作不被过度拦截；保留可回退版本 |
| 第二阶段 | 检索按任务路由，提示词与输出预算精简，分任务参数对照，时长核验 | 对照评估证明质量没有明显下降，耗时与实际成本得到改善 |
| 第三阶段 | 持久化创作简报，跨设备承接，分支和版本比较，附件专项评估 | 多路径、隔天恢复和切档案通过，关键事实不串档不漂移 |
| 持续进行 | 独立盲评、用户反馈、故障恢复与并发验收、正式配置版本核对 | 发布记录包含配置、用例、结果、限制和回退办法 |

评测基线应在第一阶段建立，并贯穿后续优化。正式修复前再次核对目标文件、部署版本和工作区变化。本计划未给出未经验证的提速比例、成本降幅、行业排名或收入承诺。
