- 测试：全量 169 个文件、3246 项通过；`tsc` 通过；后台相关文件 ESLint 0 错误、31 条警告。
- 已修复本轮发现的错误：「设为管理员」报 `42P10`（提交 `9d0f022`，已部署）。

**真实缺陷**：高 2、中 6、低 7，详见第 3 节。最严重的两项是：封禁会把付费会员降为免费（解封不会恢复）；会员到期日的编辑框用的是 UTC 日期，保存会把到期时间改早。

**局限**：内置浏览器未登录（访问 `/admin` 被跳转到登录页），我没有管理员会话，也不会代为登录。因此页面按钮的点击测试没有做，页面层面的结论来自源码阅读和接口层探测。

## 3. 缺陷清单

### 高

**H1. 封禁会把付费会员降为免费，解封不会恢复**
- 位置：[app/api/admin/users/route.ts](../../app/api/admin/users/route.ts) 第 282–290 行（封禁）、第 319–327 行（解封）
- 现象：两处 `upsert` 都写了 `plan: 'free'`。付费会员被封禁，套餐立刻变成免费；解封后仍是免费，只有 `end_date` 留着。
- 影响：封禁一个付费用户再解封，他会失去已购套餐，额度按免费版计算，且没有任何报错。
- 当前数据：没有受影响的付费用户（已通过订单为 0），属于潜在缺陷。
- 修法：封禁和解封只更新 `status` 和 `updated_at`，不碰 `plan`。没有订阅行时才插入 `plan: 'free'`（先查后写）。加一条测试：封禁后再解封，套餐和到期日不变。

**H2. 会员到期日编辑用 UTC 日期，保存会把到期时间改早**
- 位置：[app/admin/users/page.tsx](../../app/admin/users/page.tsx) 第 132 行（`toISOString().split("T")[0]`）；[app/admin/subscriptions/page.tsx](../../app/admin/subscriptions/page.tsx) 第 112 行（`s.endDate.split("T")[0]`）
- 现象：北京时间 0–8 点的到期时间，UTC 日期是前一天。编辑框显示的是前一天；保存时把 `endDate` 当作 UTC 午夜写入，到期时间会提前 0–1 天。
- 服务端：[app/api/admin/subscriptions/route.ts](../../app/api/admin/subscriptions/route.ts) 第 237 行 `new Date(endDate).toISOString()` 把日期当成 UTC 午夜，与北京时间的一天不对齐。
- 修法：前端按 `Asia/Shanghai` 取日期（`toLocaleDateString("sv-SE", { timeZone: "Asia/Shanghai" })`）；服务端把选中的日期按北京时间当天的 23:59:59 存为到期时间，并统一在一处定义「到期」的含义。加测试覆盖跨日边界。

### 中

**M1. 联网搜索密钥保存不写操作日志**
- 位置：[app/api/admin/search-key/route.ts](../../app/api/admin/search-key/route.ts) 第 12–28 行
- 现象：密钥是最敏感的配置之一，修改它没有任何留痕，操作日志页看不到。
- 修法：验证成功并保存后写 `UPDATE_SETTINGS`（或新增 `UPDATE_SEARCH_KEY`），details 只记 endpoint 和时间，不记密钥。

**M2. 多个会改数据或钱的操作没有二次确认**
- 无确认：改会员（users `saveMembership`）、会员编辑保存（subscriptions `saveEdit`）、授予管理员（permissions `grant`）、收款码启用/停用/上传（qrcodes）、运行质检回归（quality，会真实调用模型）
- 有确认：重置额度、重置密码、封禁、删除用户、撤销管理员
- 修法：统一用 `confirmDialog`；授予管理员和改收款码要求输入对方邮箱或收款方式名确认；质检回归说明耗时和费用。

**M3. 手动回归耗时约 3 分钟，前端没有超时与进度提示**
- 位置：[app/admin/quality/page.tsx](../../app/admin/quality/page.tsx) 第 64 行、第 88 行（按钮文案写着「约 3 分钟」）
- 风险：回归按用例串行调用模型（[lib/quality-regression.ts](../../lib/quality-regression.ts) 第 168 行起），每次调用的超时是 240 秒（第 129 行），整批总耗时由用例数决定，界面写的是约 3 分钟。如果反向代理的读超时是默认的 60 秒，管理员会看到「运行失败」，但服务端仍在跑、结果也会写入库。这一点要看 Nginx 配置才能确认，本次未读取（之前的权限被拒绝）。
- 修法：改成异步任务（POST 立即返回任务号，前端轮询结果）；或至少前端显示进度并在超时后提示「可能已完成，请刷新」。

**M4. 实时监控负载随用户增长，且查看内容不留痕**
- 位置：[app/api/admin/monitor/stream/route.ts](../../app/api/admin/monitor/stream/route.ts) 第 46–48 行（每 55 秒重连）；[app/api/admin/monitor/route.ts](../../app/api/admin/monitor/route.ts) 第 49–70 行（每次全量拉 24 小时生成记录、全部订单、全部用户、全部档案）
- 风险：每个打开的大屏，每次重连或收到刷新信号都重新全量查询。管理员开两个标签，压力翻倍；用户数上万后，`readAllUsers`（[lib/admin-monitor-data.ts](../../lib/admin-monitor-data.ts) 第 18 行起，每页 1000 人、逐页翻完）每次要翻 10 页以上的认证接口。
- 隐私：接口返回完整邮箱、档案名、输入内容和结果开头（注释写的是「不打码」）。查看这些内容不留痕，操作日志里只有写操作。
- 修法：聚合查询放到数据库函数里，只返回汇总；用户目录做缓存；大屏改为增量推送。隐私上建议默认打码邮箱，点击「显示」时记一条 `VIEW_USER_CONTENT` 日志。

**M5. 统计与列表在超过 1000 行后会悄悄出错（当前数据量下不影响）**
- PostgREST 默认每次最多返回 1000 行。以下查询没有分页或上限：
  - [app/api/admin/stats/route.ts](../../app/api/admin/stats/route.ts) 第 52 行（`user_quotas` 全表 `select('*')`，结果再交给 `sumFeatureUsage` 加总）
  - [app/api/admin/analytics/route.ts](../../app/api/admin/analytics/route.ts) 第 61 行（同上），第 39–42 行（活跃用户）
  - [app/api/admin/invitations/route.ts](../../app/api/admin/invitations/route.ts) 第 55–57 行（统计）、第 70 行（`listUsers` 只取第一页 1000 人，超出后新用户邮箱显示为「（用户已注销）」）
- 修法：统计改为 `count` 查询或数据库聚合函数；邮箱配对直接用已有的 `emailsByIds`（它会分页）。

**M6. 营收口径不统一**
- [app/api/admin/analytics/route.ts](../../app/api/admin/analytics/route.ts) 第 52 行按 `created_at` 统计营收；[app/api/admin/overview/route.ts](../../app/api/admin/overview/route.ts) 第 39 行「今日付费」按 `reviewed_at`。同一个「收入」，两个页面口径不同。
- 修法：定义统一口径（建议按 `reviewed_at`，即实际到账/开通的时间），两处共用一个函数。

### 低

**L1. 导出不留痕**：操作日志的 CSV 导出（服务端）没有记录导出行为；订单页「导出本页」在浏览器里完成，包含用户邮箱，也不留痕。修法：导出统一走服务端并记 `EXPORT_DATA` 日志。

**L2. 角色没有分级**：概览页有 `developer`、`admin`、`operator` 三种角色的中文名，但所有后台路由只调用 `requireAdmin()`，不论角色，权限完全相同，任何管理员都能删用户、授予管理员。修法：先定义权限矩阵（谁能删用户、授权、改收款码、导出），再在 `requireAdmin` 之上加按权限校验的函数。

**L3. 概览的快捷入口不全**：缺邀请码、质检看板、数据分析、权限管理、联网搜索密钥。另外「权限管理」与「质检看板」都用 `ShieldCheck` 图标，难以区分。

**L4. 手机端表格**：[components/admin/kit.tsx](../../components/admin/kit.tsx) 的 `DataTable` 是横向滚动（`min-w-[40rem]`），没有卡片布局。用户行有 6 个按钮，手机上很挤。修法：小屏改为卡片列表；按钮收进「更多」菜单。

**L5. 代码质量警告**：后台相关文件 ESLint 31 条警告、0 错误。其中 15 条是 React 规则「在 effect 里同步 setState」，2 条是渲染中调用不纯函数（如 `Date.now()`），1 条是渲染中读 ref，13 条是 `any`。

**L6. 字段命名**：`/api/admin/stats` 的 `apiCallsToday` 实际是「累计生成次数」，代码注释里承认了这一点。修法：前端改用 `totalGenerations`，删掉旧字段。

**L7. 环境文件格式**：服务器上的 `.env.local` 第一行有 `yyyy#`，用 shell `source` 时报 `command not found`。Next.js 的 dotenv 解析是否受影响未验证，应该清理掉这一行。

## 4. 多维度分析

**安全**
- 优点：所有后台接口先 `requireAdmin`；`service_role` 只在鉴权之后使用；临时密码只返回一次、不进日志；凭证用 30 分钟签名链接；撤销自己和删除管理员被禁止；删除用户要先预览、输入邮箱确认。
- 缺口：应用层没有要求管理员二次验证（代码里没有检查 MFA）。管理员能审核收款、重置密码、删除用户，账号一旦被盗，危害很大。建议启用 Supabase MFA，并对高危操作要求近期重新验证。
- 缺口：没有权限分级（见 L2）；导出和查看用户内容不留痕（见 L1、M4）。

**数据一致性与事务**
- 订单审核是多步写入（改订单状态 → 写会员 → 清额度），靠代码里的回滚。如果进程在中间崩溃，订单可能停在 `approved` 而会员没开通。现在的回滚只覆盖「代码能走到的失败」。
- 建议：把审核和开通做成一个数据库函数（与现有的 `kaiwu_*` RPC 同一模式），一个事务内完成，失败整体回滚。
- 封禁状态有两处（认证层 `banned_until` 与订阅行 `status`），需要同步；H1 就是在这里出的问题。建议用一个函数统一写两处。

**性能与可扩展性**
- 反复全量扫描认证用户（`scanAllUsers`、`countAuthUsers`、`countNewUsers`），用户数上万后每次请求会慢。
- 监控大屏是全量查询（M4）。
- 统计与列表有 1000 行上限隐患（M5）。
- 建议：用户邮箱映射做成数据库函数（`SECURITY DEFINER`，只返回 id→email），一次查询完成；统计用聚合函数。

**可靠性与可观测性**
- 错误只进 pm2 日志，没有告警。健康探测的通知脚本已经做好（今天上线），还差群机器人地址。
- 夜间质检回归的结果写入了库，但失败时没有通知。
- 建议：关键定时任务（夜间回归、备份）失败时也推送通知。

**测试**
- 现有测试以源码扫描为主（检查代码里有没有某段文字、某个写法），行为测试较少，没有端到端测试。
- 今天的 `42P10` 问题就是「代码与数据库约束不一致」，现有测试抓不到，因为它不跑真实数据库。
- 建议 1：写一个「契约测试」，从迁移文件解析 `UNIQUE` 约束，与代码里每一处 `onConflict` 对照，不一致即失败。
- 建议 2：用本地 Supabase（Docker）跑一组后台的端到端测试：授予管理员、延期、通过/驳回订单、封禁/解封、生成/作废邀请码、收款码启用/停用、导出。
- 建议 3：对 H1、H2 补行为测试（见上）。

**体验与交互**
- 信息架构合理：导航分组清楚，「订单审核」「系统设置」的主次分开，每个页面都有空状态和错误状态（`kit.tsx` 统一）。
- 术语不统一：「会员」与「订阅」混用；「清额度」「重置额度」「重置配额」并存；「封禁」的状态来源（认证层还是订阅行）用户看不出来。建议统一为「会员套餐」「额度」「账号状态」。
- 危险操作的确认方式不统一（M2）。
- 手机端：菜单抽屉和顶栏做得好；表格和监控大屏仍不适合手机（L4，监控页见既有记录）。

**架构与代码**
- 业务逻辑留在路由里，`orders/review` 约 200 行。建议把审核、开通、额度清零抽成服务函数（或数据库函数），路由只负责鉴权和参数。
- 创建 Supabase 客户端的方式不统一：`users`、`orders/review` 在模块级创建，其他路由用 `getServiceSupabase()`。
- 疑似废弃的表（需要确认后再决定，删除需要你授权）：`admin_action_logs`（代码未使用，与 `admin_logs` 并存）、`payments`、`user_subscriptions`、`usage_records`、`quota_plans_backup_20260812`、`system_config`。
