# 开物用户视角体检报告（2026-10-23）

> 承接 [用户视角体检_20261020](用户视角体检_20261020/开物用户体验与产品发展体检报告.md) 和 [整改优化方案_20261017](整改优化方案_20261017.md)。
> 本次以一个第一次进入、想做出可拍内容的编导或运营的角度，过一遍产品：体验、功能、稳定性、商业化。
> 每条判断都标明依据：**代码**（读源码确认的行为）、**线上**（只读检查服务器或数据库的结果）、**数据**（夜间回归与实时体检的统计）、**判断**（基于经验的分析，需要用户验证）。

## 一、结论先说

**开物有一个别的工具少见的核心：围绕同一个账号连续工作。** 档案（多账号、人设事实、禁忌）、定位、简报、选题到脚本到分镜的接续、作品与录数据、月报，这些串起来，才让它不只是一次性的 AI 写稿。这个方向应该保留。

**但它现在更像一个功能很全、需要先学习才能用好的工作台，而不是"打开就能得到一份可拍结果"的工具。** 三个问题最突出：

1. **第一次拿到可用结果太慢。** 生成前必须先完成「建档 → 账号定位 → 创作简报」三步，首页和导航又有大约 30 个入口。熟手觉得完整，第一次进来的人会先被要求理解一套体系。
2. **结果的可信度和可用性在拉扯。** 事实守卫是对的，但结果里大量「【待确认】」占位，需要用户自己补；同时实时体检的通过率只有约 48%，夜间回归的阻断失败几乎每晚都有。用户拿到的常常是"还要改"的草稿。
3. **交付链路有几处会丢东西或让人不放心。** 保存失败只打日志；月报可能漏算；拍摄标记只存在当前浏览器；线上还有偶发的 502 和部署后的 Server Action 失效。

**建议的定位不变：专业编导、代运营和小团队的创作交付工作台。** 不建议把它卖成「零基础一键出片」，那会同时放大第 1 和第 2 个问题。

## 三、用户旅程体检（按第一次进来的顺序）

### 3.1 进门：门票与信任
- **做得好的**：邀请制能控制测试范围，产品方有明确的管理手段。
- **不好的**：潜在用户在联系客服之前，看不到产品适合谁、会交付什么、用户会得到什么。没有任何免费样例、脱敏成品或任务演示。（判断）
- **风险**：如果后续要扩大试用，这里是第一道门槛。

### 3.2 第一次使用：三步地基
- **现状**：生成前必须先有档案；定位和简报各一步。质量守卫的规则是「没有地基，不生成创作结果」（2026 年 10 月 23 日，今天上线）。
- **好处**：生成的内容有依据，减少通用答案。
- **代价**：第一份结果前要做三步，等于第一次体验的时间成本被大幅拉长。源码里保留的一条历史漏斗（注册 10 人、建档 10 人、定位 4 人、简报 1 人）已经很久没有更新，不能当作当前数据，但它说明这个代价是真实的。（代码注释 + 判断）
- **建议**：保留地基的价值，但把「第一份结果」和「完整地基」分开。例如先用 5 个必填问题（做什么、给谁看、这次目标、真实卖点、能怎么拍）生成一份**有边界的**结果，结果上明确标出"未建定位，仅按这次信息生成"，然后引导补地基。这需要产品方决定，因为它和「没有地基不生成」的要求直接冲突。

### 3.3 找入口：信息架构
- **现状**：侧栏约 30 个入口，分组是「开始创作 / 先打地基 / 更多工具」。选题、方向、内容规划、账号定位、内容定位、创作简报、行业建议之间的边界，即使是熟手也要想一下。
- **判断**：这些板块是按工程模块长出来的，不是按用户任务排列的。用户想的是"我有稿子要改"、"我要写选题"、"我不知道拍什么"，而不是"我要用内容规划还是创作方向"。
- **建议**：首屏只问用户要做哪一类任务（已有稿子改、已有题目写、不知道拍什么、为客户做整套规划），按任务进入最短路径。其它板块放进「全部工具」。

### 3.4 生成内容：质量与可用性
- **做得好的**：事实守卫、禁忌检查、违禁词标红、「待确认」占位、画布修改、版本、收藏。这些防护在同类工具里很少见。
- **不好的**：
  1. **占位太多，草稿感强。** 没有案例、没有价格时，结果里充满「【待确认】」。用户拿到的是需要自己补的草稿，不是可拍稿。（判断，有数据支持：见第五节）
  2. **快速模式不是默认。** 脚本页打开就是全部设置，快速模式要在下面才找得到（代码：`quickMode` 默认 `false`）。
  3. **结果长，关键段落不突出。** 审稿结果里分析、完整稿、纯文字文案重复出现，用户要自己找哪一段能用。（上一份报告 Q02，未核实本次是否改变）
  4. **改稿没有对照。** 「只改第二段」之类的要求，无法逐处看到改了什么、动没动事实。（Q03，未改）
- **建议**：默认先给「可用稿 + 必须处理的问题 + 待确认清单」，分析折叠。小改任务只显示改动处。

### 3.5 保存与找回：信任的底线
- **现状**：脚本生成后，历史保存失败只写控制台，用户看不到任何提示，也没有重试或本地草稿。（代码：`app/dashboard/script/page.tsx` 第 583、618 行）
- **判断**：这是现在最危险的一条。用户看到了结果、以为已经保存，刷新后找不到，只能重新生成，也就是重新扣额度。
- **建议**：立即修：显示「保存中 / 已保存 / 保存失败」；失败时保留本地草稿并提供重试和复制。这个改动小，收益大。

### 3.6 拍摄与交付：编导最在意的环节
- **做得好的**：拍摄交付包、口播大字稿、镜头清单、素材位置，这些比继续堆文案模板更贴近真实拍摄。
- **不好的**：
  1. 拍完标记只存在当前浏览器（F03），电脑准备、手机拍摄、交给摄影师都接不上。
  2. 没有客户审阅、批注、定稿确认（F04）。代运营和多客户场景几乎无法在产品内完成交付。
  3. 没有作品的统一视图：选题、定稿、分镜、封面、发布、数据分散在不同页面。
- **建议**：先做镜头完成状态的服务端同步（跨设备），再做只读审阅链接和定稿确认。

### 3.7 发布与复盘
- **做得好的**：「待录数据」卡和 3 个数的快速录入（B1）是很好的设计，把数据录入的门槛降到了最低。学习进度提示也让用户知道离生效还差多少。
- **不好的**：
  1. **月报可能漏算。** 报告页拉 200 条作品，接口一次最多返回 50 条，超过 50 条的作品可能不在报告里，而月报是给客户看的。（F01，未修复）这是信任问题，应该优先修。
  2. 月报读取失败时，可能生成「发布 0 条」的报告。（F02，未重新核实）
  3. 没有发布排期和日历。
- **建议**：先修月报的完整统计（按月份在服务端统计，显示统计范围和缺失数量）。

### 3.8 付费与额度
- **做得好的**：会员和次数包的计量逻辑已有基础（次数包有扣减顺序的注释，会员额度每期清零，次数包长期有效）。
- **不好的**：
  1. **额度按功能拆分，用户很难预测一次创作要扣多少。** 基础、专业、高频的月价在上一份报告里记为 49、99、199 元，各功能的额度规则不同。（B03，未改）
  2. **次数包已经面向所有用户开放销售**，但上一份报告提到的几件事都还没有看到答复：有效期、退款规则、是否限购、盈利核算。（判断：这是风险较高的一步）
  3. 人工付款，当天审核，不开发票（B02）。企业采购和报销基本走不通。
- **建议**：先给出三类任务的用量示例（只审一次稿、从选题做出一条完整内容、为客户规划一批）；生成前显示本次扣哪个额度；次数包的条款和盈利核算在扩大销售前完成。

### 3.9 稳定性与速度
- **502 偶发**：当前 Nginx 错误日志里仍有 30 条「upstream sent too big header」，报错的请求多为带登录 Cookie 的页面请求。用户看到的是 Nginx 默认的 502 页面，没有任何引导。（线上，已在 10 月 23 日排查，修复方案已给出，尚未执行）
- **部署后 Server Action 失效**：应用错误日志的最后 2000 行里，有 663 条「Failed to find Server Action」。最可能的原因是部署重启后，仍停留在旧页面的用户调用了旧的服务端动作。（线上，原因为判断，未复现）如果属实，每次部署都会打断正在使用的人，需要在部署流程里处理。
- **等待**：深度研究的耗时在代码和文档中写的是约 3 分钟，较长任务没有可靠的进度和中断恢复说明。（上一份报告 Q06，未重新测量）
- **服务器**：2GB 内存的单机，构建和部署都要小心。今天检查时内存可用约 1.4GB，负载正常。风险在于没有冗余，机器一出问题，整站都不可用。

### 3.10 测试与质量保障
- **做得好的**：单元测试 281 个文件、约 4500 条用例，全部通过；夜间回归用固定档案真实调用模型；实时体检每次生成都跑。
- **不够的**：没有浏览器级的端到端测试。关键路径（建档 → 定位 → 简报 → 生成 → 保存 → 月报）没有自动化覆盖，线上只能靠人工点检和夜间回归发现问题。（代码：`package.json` 里只有 `vitest` 和 `eslint`）

## 四、做得不好的地方（直说）

1. **第一次有用结果太慢。** 三步地基是产品决定，但没有用数据验证它值不值得这个代价。
2. **结果里待确认太多。** 对用户来说，「草稿」和「可拍稿」之间差的正是那些占位。
3. **保存失败静默。** 用户以为保存了，实际可能没有，这是丢稿的直接原因。
4. **月报可能漏算。** 给客户看的数字不完整，比没有功能更伤信任。
5. **拍摄标记只在本地。** 说明文字写得很清楚，但它就是功能缺口。
6. **侧栏入口太多，名字接近。** 熟手能分清，新手分不清，且很多入口是按工程模块划分的。
7. **提示与规则不一致。** U02 的徽章仍在误报「没生成简报」。用户会以为自己的资料没保存。
8. **次数包在条款和盈利没确定时就开放销售。** 这一点要尽快补齐，否则定价风险会先于产品问题暴露。
9. **线上偶发 502 和部署后的 Server Action 失效，用户只看到错误页面。** 没有引导和恢复路径。
10. **质检通过率低，用户感知到的是"经常有红色提醒"。** 其中有相当一部分是规则误报（今天已经找到年限、禁忌引用等几类），但在修完之前，内部指标和用户感受都不好看。

## 五、质量数据（用来判断"好不好用"）

数据来源：实时体检（每次生成后，最近 14 天，63 条）、夜间回归（每晚 7 个用例，最近 16 轮）。统计口径：阻断项。

- **实时体检通过率约 48%**（30/63）。失败主要是「禁忌词」和「关键事实没有出处」。其中禁忌词有相当一部分是引用原稿，已在 10 月 23 日修正。
- **夜间回归每晚都有阻断失败**：北京时间 10 月 19 日至 23 日凌晨的 5 次，通过数分别为 2、2、4、3、5（共 7 个用例）。没有一次全部通过。
- **失败最集中的用例**：美甲选题（16 轮里失败 14 次，主要是事实和年限）、无价格引流脚本（12 次）、创作方向（12 次）。
- **注意：部分失败是规则误报。** 比如「在杭州开美甲店 1 年」被当成居住年限，「碰到的姐姐做了 9 年」被当成作者经历。这些已经修复，但需要看下一轮夜间回归才能确认效果。

**判断**：这组数据说明质量还不稳定。对用户来说，主要影响是"经常要自己改"。在误报清理之前，不能用这些数字判断产品质量到底差多少。

## 六、功能欠缺（按用户价值排序）

| 优先级 | 功能 | 为什么需要 | 现状 |
|---|---|---|---|
| 高 | 客户审阅与定稿确认（只读链接、批注、版本） | 代运营和多客户交付的核心 | 没有 |
| 高 | 可靠的保存状态与草稿恢复 | 防止丢稿 | 仅控制台日志 |
| 高 | 月报完整统计 | 给客户看的数字必须完整 | 最多 50 条，可能漏算 |
| 高 | 改稿对照（逐处接受、撤回） | 编导最常见的「只改一句」 | 只有版本和画布 |
| 中 | 作品为中心的统一视图 | 选题、定稿、分镜、封面、发布、数据集中在一处 | 分散在多个页面 |
| 中 | 拍摄进度跨设备同步 | 电脑准备、手机拍摄 | 仅本地 |
| 中 | 发布排期、待拍待发待复盘的首页排序 | 把工作从"功能目录"变成"今天要做的事" | 有待录数据卡，没有排期 |
| 中 | 学习依据与纠正入口 | 让用户相信「越用越懂你」 | 只有进度 |
| 中 | 封面模板、品牌色、多比例安全区 | 客户品牌的日常需求 | 基础大字版 |
| 低 | 对标账号持续追踪、热点数据源 | 需要稳定的合法数据来源 | 人工录入，实时热点靠搜索 |
| 低 | 团队权限、多人协作后台 | 规模变大之后才需要 | 没有 |
| 低 | 语音输入之外的移动端专门体验 | 拍摄现场的使用 | 未验证 |

## 七、未来方向

### 7.1 定位
保持「专业编导与代运营的创作交付工作台」。不做大众化的一键出片，也不急着做完整剪辑、AI 视频生成和全平台自动发布。

### 7.2 三阶段路线（建议）

**第一阶段（约 2 周）：先让一条内容可靠地完成**
- 保存状态可见，失败可重试（Q05）。
- 月报完整统计（F01），错误不打印成零业绩（F02）。
- U02 的徽章误报修正。
- 快速模式变为默认入口（U03），高级设置可展开。
- 夜间回归的误报清理，目标：连续 3 晚阻断失败为 0。
- 修复 502：执行已给出的 Nginx 缓冲区调整。
- 排查部署后的 Server Action 失效：确认是否是旧页面导致，并在部署流程里处理（例如部署后提示刷新，或保留旧版本一段时间）。

**第二阶段（约 3 至 6 周）：让专业用户每天回来**
- 作品为中心的统一视图，首页按「待确认、待拍、待发、待复盘」排序。
- 改稿对照：逐处接受或撤回，明确是否动了事实。
- 拍摄进度跨设备同步（镜头状态、备注、最后修改时间）。
- 发布排期与复盘。

**第三阶段（之后）：多客户交付**
- 只读审阅链接、批注、定稿确认，明确每次确认的是哪一版。
- 客户化月报和品牌封面模板。
- 团队权限从单份作品的授权开始，不做大而全的团队后台。

### 7.3 商业化
- **次数包**：在条款（有效期、退款、限购）和盈利核算确定前，不做大规模推广。
- **企业采购**：先列出能提供的票据、合同和服务范围，再谈开发票和企业支付。
- **获客**：在门票页增加少量脱敏成品和适用人群说明，让没有门票的人也能判断是否适合自己（B01）。

### 7.4 工程与验证
- **增加浏览器级冒烟测试**，覆盖关键路径：建档 → 定位 → 简报 → 生成 → 保存 → 月报。
- **大文件拆分**（脚本页 65KB、首页 37KB），在改到这些文件时顺手做，不单独排期。
- **建立固定的真实任务验收集**：一人拍摄、没有案例、只改一句、旧档案与新材料冲突、分镜不改台词、断网后恢复。每次模型或提示词调整后复测。

## 八、要跟踪的指标

10 月 20 日报告提出的六个指标仍然适用，但目前**没有可信基线**：

| 指标 | 建议口径 | 现状 |
|---|---|---|
| 首次有用结果用时 | 从进入到用户确认第一份结果可用 | 没有记录 |
| 稿件可用率 | 用户评价「可直接用 / 小改可用 / 需重做」 | 没有记录 |
| 事实问题率 | 固定样本人工审查 | 夜间回归能部分覆盖 |
| 内容完成率 | 从生成到定稿、拍摄、发布 | 没有完整链路记录 |
| 有效复访率 | 返回后确实完成了创作或交付 | 没有记录 |
| 单份可用结果成本 | 模型、重试、长任务、人工支持成本除以可用结果 | 没有记录 |

**建议**：先用已有的漏斗埋点（`funnel_events` 相关迁移已经存在）记录「首次有用结果」，再决定其它指标的口径。不要用生成次数或测试通过数替代这些指标。

## 九、用户验收任务（建议保留）

1. **短视频运营**：已有选题，写一条 60 秒、单人可拍的口播；不能编造客户案例；拿到正文后能快速改一句。
2. **代运营**：在两个客户档案之间切换，确认材料、历史、偏好和月报分别归属正确；把定稿交给客户确认。
3. **编导**：导入原稿，只把第二段改口语化；保留原话、数字和段落；分镜沿用确认后的同一版台词。
4. **拍摄人员**：电脑准备后，用手机打开交付包，找到镜头、台词和待确认项，标记完成后在电脑上能看到。
5. **企业内容负责人**：获取指定月份的完整报告，分清缺数据和零数据；确认采购、票据和服务范围是否满足需要。
6. **低频用户**：理解一次购买能做什么，成功、失败、中断各如何扣额度。

建议找 5 到 8 名符合这些角色的真实测试者观察完成过程。这是下一轮研究的建议，本报告没有做用户访谈。

## 十、局限与未验证事项

- **没有真实用户访谈、转化和留存数据。** 上面的判断大多来自源码和运行数据，需要用真实任务验证。
- **没有做手机真机测试。** 拍摄现场、键盘遮挡、视频上传、弱网恢复都没有验证。
- **没有重新生成新的模型样本。** 质量判断依据的是夜间回归和实时体检的已有记录，其中包含规则误报。
- **没有逐页打开全部 20 条上一份报告的问题。** 标「未重新核实」的，是本次没有看到新证据，不代表已经修好或没修好。
- **线上状态只做了只读检查。** 没有模拟断网、保存失败等故障，也没有实际支付或扣费。
