# 开物全身体检报告（2026-10-17）

> 范围：功能覆盖、用户体验、报错与文案、工程健康。
> 方法：读代码、数文件、查界面文字、跑 lint 和测试；**没有**在真机、线上真实用户数据、真实模型输出上复测。能查到的数都注明了来源。

---

## 一、结论先说

1. **最该先修的是「内部话漏到用户面前」**：迁移没执行时，用户会直接看到「请先在 Supabase 执行 xxx.sql」「数据库还没升级，请联系管理员」这类话。这是体验硬伤，也是运维暴露。
2. **最大的体验漏斗在「建档 → 定位 → 简报」**：线上数据（记录在引导页代码注释里，未在本次复测）是建档 100%、做完定位 40%、做到简报 10%。简报正是让选题、脚本真正用上账号信息的那一环。
3. **功能上最明显的缺口**：评论区用户真实问题进选题、拍摄素材（视频文件）管理、给客户的月报导出、发布日历与提醒、封面图。
4. **工程上最大的隐患**：57 个迁移文件没有统一的状态页，功能缺表时会静默降级，管理员不知道哪一个没跑。

## 三、功能上还缺哪些

| 优先级 | 缺口 | 为什么重要 | 现状 |
|---|---|---|---|
| P1 | **评论区真实问题 → 选题** | 编导最常用的选题来源是评论区的高频问题 | 只有档案里手填的「粉丝常问」（`fan_common_questions`），没有导入与归纳 |
| P1 | **发布日历与提醒** | 内容规划给出了条数，但没有「哪天发、什么时候拍」 | `content-plan` 只到方向；7 天计划是列表，没有日历和提醒 |
| P1 | **给客户 / 老板的月报** | 编导常服务多个门店或客户，要给对方看结果 | 有数据导出（`DataExportCard`）和素材导出，没有「可以直接发给老板的月报」 |
| P1 | **拍摄素材管理** | 拍完的视频文件没地方放，只能在别处存 | 素材库只存文字（真实素材、好稿、AI 建议） |
| P1 | **自动数据回流** | 现在要人工粘贴或录入，数据常常断档，影响偏好学习的样本 | 已有粘贴导入（`MetricsImport`），没有自动同步（平台接口受限，需要单独评估） |
| P2 | **对标账号持续追踪** | 对标账号只在档案里写名字，没有持续看它在做什么 | 只能拆单条视频，没有跟踪 |
| P2 | **热点与实时数据** | 追热点依赖实时数据，目前没有稳定来源 | 之前的记录里就有这个未决项（需要确定数据源） |
| P2 | **封面图 / 视觉** | 标题封面只给封面大字建议，编导还要自己做图 | 没有封面模板或生成 |
| P2 | **团队协作** | 编导、拍摄人、老板常常是不同人 | 单账号单人使用，没有分享或评论 |

## 四、工程体检（不直接影响用户，但影响后续速度和稳定性）

| 项目 | 结果 | 说明 |
|---|---|---|
| lint | 0 个错误，262 个警告 | 其中 `@typescript-eslint/no-explicit-any` 109 个（`app` 4 处、`lib` 3 处 `as any`，其余来自 lint 统计口径，见下） |
| 大文件 | 脚本页 87KB、首页 83KB、选题页 77KB、自由对话 71KB | 单文件过大，改一处容易牵动别处 |
| 迁移 | 57 个 SQL 文件 | 没有统一台账，没有「哪些已执行」的状态页；功能缺表时各自降级，问题只在用户那边显现 |
| 测试 | 204 个文件、约 3684 条，全量约 4 分钟 | 在机器忙时，多个需要冷启动大模块的用例会超时（这段时间已把全局超时放宽到 30 秒）。能通过，但有偶发性，说明测试本身偏重 |
| 质量评估 | 有质检规则（`lib/quality-checks.ts` 45KB），没有定期跑真实模型输出的回归 | 改提示词后，没有一套固定样本来判断质量是涨是跌 |

> 注：`as any` 的 4 处在 `app`、3 处在 `lib` 是 grep 统计；lint 的 109 个 `no-explicit-any` 包括其他写法，两个口径不同，以 lint 为准。

## 五、已知但还没处理的（来自之前的记录，未在本次复测）

- 选题与方向的内容仍可能带有没有出处的说法（「承诺免费送货」「1000 元挑战」）。检查程序能抓到，但模型仍会写。
- 脚本形式有时会从「店主口播」变成「街访」，需要顾客配合，和「只有店主一个人」的约束冲突。
- 「本轮内容落实规则」之类的内部标题有输出过滤（`lib/output-guard.ts` 的 `LEAK_HEADING` 已覆盖），但线上效果没有逐条验证。
- 免费额度的调整问题，产品方还没有给结论。

## 七、建议的顺序

1. **先修 P0**：内部迁移话改成用户能懂的话；加一个管理后台的「迁移状态」页，列出 57 个迁移哪些已执行。
2. **再修漏斗**：首次建档分两步（必填 5 项 + 前采建档入口）；定位完成后自动引导到简报。
3. **然后做首页和侧栏的收敛**：按阶段只露 1～2 张主卡，侧栏加「下一步」高亮。
4. **功能上先补两个**：评论区 → 选题，发布日历与提醒。这两个直接对应编导每天的工作。
5. 工程上：拆大页面，把 `any` 清掉一部分，建立一套固定样本的质量回归。
