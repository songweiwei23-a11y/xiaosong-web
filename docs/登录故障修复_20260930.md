# 登录故障修复与正式发布

用户要求立即修复偶发登录报错、登录不上和加载慢；原有 Claude 设计、排版与风格保留。

## 已确认并修复

1. `middleware.ts` 的旧 Cookie 适配器每写一个 Cookie 都重新创建响应，刷新后的分块登录 Cookie 会丢失前面的块，重定向也没有携带刷新结果。改为 `getAll/setAll` 批量更新请求 Cookie，所有放行、重定向和临时故障响应完整回写 Cookie 与防缓存头。
2. 登录成功同时 `router.push`、`router.refresh`，且 `finally` 会重新开放提交按钮。改为一次整页导航，同步提交锁保持到交接；重复点击、迟到的初始会话探测、卸载后的异步结果不会重复导航。注册后的重试目标保留 `/onboarding`。
3. Supabase 认证请求没有明确等待上限。新增 `lib/supabase/fetch.ts`，认证请求每次 12 秒、其他 Supabase JSON 请求每次 15 秒真实 AbortController 取消，截止时间包含正文读取。接入浏览器客户端、用户服务端客户端和 middleware。保留原来直连 Supabase HTTPS，不增加同源密码代理。
4. 初始会话探测缺少失败处理；注册请求也可能一直等待。探测失败保留表单；注册请求及正文读取设 30 秒取消，不自动重复注册，超时提示先尝试登录确认账号是否已经创建。
5. 临时认证故障被误判为未登录。middleware 与两个 API 守卫明确区分失效会话和临时认证故障：前者保持登录重定向/401，后者返回可重试 503，不主动登出、清 Cookie 或放行受保护数据。管理员实时 `getUser`、封禁 403、额度 402 和原有权限规则保留。
6. 浏览器禁用 localStorage 时，档案切换通知会触发自身再次加载，又读不到新选择，形成请求循环。增加本次页面会话内的内存兜底和重复选择去重，同一档案编辑通知仍保留。
7. 首页配额接口的套餐、额度和月用量互不依赖，改为同时查询，减少一次数据库往返等待。

普通受保护页面以 SDK `getClaims()` 验证 JWT 签名和有效期；对称签名由 SDK 回退 `getUser()`。各数据 API 继续独立验证用户和权限，管理员页面继续实时校验用户。

## 后续协作边界

- SDK 自带刷新重试保留；连续网络故障时，旧会话恢复可能等待约 36 秒。每次网络请求已经有取消上限，密码登录没有额外自动重试，注册也不重试。
- 已检查当前 auth-js 的旧刷新提交保护：成功路径对比前后刷新令牌，失败路径重新检查当前有效会话，常见迟到结果不会覆盖已成功的新登录。刻意延迟异步内存删除的合成测试能制造更窄的 SDK 内部事务竞态，未在线上或真实浏览器自然复现；未修改依赖或增加会拖慢正常登录的初始化等待。
- 当前工作区中还有此前已经发布的实时监控、历史记录和文案改动，以及其他协作者的文档。不得用 Git 重置覆盖这些内容；本次没有更改宣传页面设计或业务数据。
